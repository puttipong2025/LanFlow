# ส่วนที่รับ–จ่าย PWA ใช้ร่วมกับบิลยางได้

ตรวจเมื่อ: 2026-10-31

สถานะ: ผลสำรวจและข้อเสนอด้านล่างบันทึกจาก source ณ 2026-10-31 ผู้ใช้สั่งเริ่มครบทุก Phase แล้วเมื่อ 2026-11-01 ระบบปัจจุบันและผลทดสอบหลังแก้อยู่ [verification ledger](income-expense-numbering-verification.md) และ [rollout runbook](income-expense-numbering-rollout.md); ข้อความอธิบายของเดิมด้านล่างเป็นหลักฐานก่อนพัฒนา ไม่ใช่สถานะรอเริ่มปัจจุบัน

ขอบเขต: นำระบบเลขบิลยางมาปรับใช้กับรายรับทั่วไปและรายจ่ายทั่วไป ตาม [ข้อตกลงรับ–จ่าย](income-expense-device-numbering-design.md) และ [ADR 0094](adr/0094-income-expense-device-base-and-central-suffix.md) ไม่รวมเปลี่ยนเลขบิลขายหรือรายการที่มาจากโมดูลอื่น

## ข้อเสนอหลัก

ใช้โครงสร้างออฟไลน์ร่วมที่มีอยู่ต่อ และแยกส่วนทะเบียนเครื่อง/รูปแบบเลขออกจากข้อกำหนดบิลยางเท่าที่จำเป็น คงทางบันทึกและอนุมัติธุรกิจของแต่ละโมดูล ไม่ย้ายรับ–จ่ายทั้งหมดไปเข้าคิวกลางบิลยางเพื่อทำเลขบิล

## ส่วนที่ควรใช้ร่วมเพิ่ม

### 1. ทะเบียนเครื่องและหน้าจัดการ

ใช้ทะเบียนเดิมของบิลยางสำหรับทั้งสามชุดเลขตามที่ผู้ใช้ยืนยันแล้ว: บิลยาง รายรับ และรายจ่าย รหัสเดียวในเบราว์เซอร์/โปรไฟล์และสาขาเดียวกัน ไม่สร้างทะเบียนคู่ขนานให้รับ–จ่าย

หลักฐาน: `src/lib/rubber-bills/numbering-idb.ts` (`prepareRubberBillIssuer`, `rubberNumberingReady`), `src/app/api/lanflow/rubber-bills/issuers/route.ts`, `src/components/lanflow/OfflineReadinessStatus.tsx`, `src/components/admin/RubberBillIssuers.tsx` และ migration `20261031020000_rubber_device_bill_numbers.sql` ร่วมกับ `20261031021000_rubber_issuer_management_guards.sql`

ข้อเสนอ: แยก Module สำหรับทะเบียนเครื่องที่ซ่อนรายละเอียดการเตรียมรหัส การตรวจความพร้อม และการติดต่อซ้ำ โดยคง endpoint/ฟังก์ชันเดิมไว้ให้บิลยางและคิวเก่าใช้งานได้ หน้าจัดการเดิมใช้ร่วมได้โดยตรวจข้อความให้ครอบคลุมทั้งสองโมดูล ไม่จำเป็นต้องเปลี่ยนชื่อ table หรือทำทะเบียนใหม่เพียงเพื่อเปลี่ยนชื่อในโค้ด

ผู้ใช้ยืนยันให้หลายแท็บและหลายบัญชีในเบราว์เซอร์/โปรไฟล์และสาขาเดียวกันใช้รหัสเครื่องและลำดับต่อกันภายในชุดประเภท/วันที่เดียวกัน โดยยังแยกร่าง งานรอส่ง และชื่อผู้สร้างตามบัญชีเมื่อ 2026-10-31 และยืนยันการเลิกใช้รหัสร่วมแล้ว: รับรหัสใหม่เมื่อกลับออนไลน์สำหรับรายการใหม่ คงเลขและงานเดิมให้ส่งต่อได้ตามสิทธิ์ ไม่ลบงานค้างหรือถอน login เครื่องออฟไลน์ใช้รหัสเดิมได้จนทราบการเลิกใช้

### 2. ตัวช่วยรูปแบบเลขและการตรวจเลขท้าย

`src/lib/rubber-bills/numbering-contract.ts` มีการตรวจข้อมูล issuer การจัดวันที่/ลำดับ และการตรวจว่าเลขยืนยันเป็นฐานเดิมตามด้วยเลขท้ายจำนวนเต็มบวก ใช้หลักการร่วมได้ โดยตัวจัดรูปแบบรับ–จ่ายเติม `I-` หรือ `E-` ตามประเภท

ข้อเสนอ: แยกตัวช่วยที่ใช้ร่วมจริง เช่น ตรวจ issuer และตรวจเลขท้ายออกจากชื่อบิลยาง คงตัวตรวจและตัวจัดรูปแบบเดิมสำหรับบิลยางไว้เป็นทางเรียกที่เข้ากันได้ รูปแบบและ payload ของบิลยางเก่าทั้งสองรุ่นต้องยังยอมรับได้ ไม่เพิ่มรหัส `I/E` ลงในเลขยาง

### 3. การบันทึกเลขพร้อมงานรอส่งในครั้งเดียว

`enqueueNumberedRubberCreate` ใน `src/lib/rubber-bills/numbering-idb.ts` บันทึก counter, reservation และ outbox ใน IndexedDB transaction เดียว และคืนผลหลัง transaction สำเร็จ แนวทางนี้นำมาใช้กับรับ–จ่ายได้ เพื่อไม่ให้แสดงเลขว่าบันทึกแล้วทั้งที่งานรอส่งยังไม่ถูกเก็บ

ข้อจำกัด: เรียกฟังก์ชันเดิมกับรับ–จ่ายโดยตรงไม่ได้ เพราะรับชนิด `RubberBill` ใช้ `billDate` ตรวจ reservation เป็นเลขยาง และใส่ metadata ลง payload ยาง ตัวนับปัจจุบันแยกด้วยวันที่เพียงอย่างเดียวภายใน state ของทะเบียนนั้น

ข้อเสนอที่กระทบบิลยางน้อย: ใช้ทะเบียนร่วม แต่แยกข้อมูลลำดับและ reservation ของ `I/E` ให้ชัดตาม issuer/type/date พร้อมบันทึกเลขและคิวรับ–จ่ายใน transaction เดียว คง counter และ reservation บิลยางเดิมไว้ การเพิ่มพื้นที่เก็บต้องมีการอัปเกรด IndexedDB ที่รักษาคิวและสถานะเดิม ไม่ย้ายข้อมูลหรือรีเซ็ตแบบไม่มีหลักฐาน

### 4. การยืนยันผลก่อนเก็บเลขเต็มและนำงานออกจากคิว

บิลยางมีตัวตรวจผลที่อิงคำสั่งและเลขฐาน เช่น `src/lib/rubber-bills/sync-result.ts` และ `central-sync.ts` ส่วนรับ–จ่ายมี `src/lib/income-expense/contracts.ts` และ `background-command.ts` อยู่แล้ว แต่ตัวตรวจผลสร้างรายการปัจจุบันยังไม่ตรวจ `serverBillNo` ว่าเป็นฐานเดิมบวกเลขท้าย เพราะยังไม่มีสัญญาออกเลขนี้

ข้อเสนอ: ใช้ตัวตรวจความสัมพันธ์ฐาน–เลขท้ายร่วมกัน แล้วเพิ่มเข้า contract รับ–จ่ายทั้ง route ตัวซิงก์หลัก การลองซิงก์รายรายการ และผลหลังอนุมัติ คง validator ของผลธุรกิจแต่ละโมดูลแยกกัน อย่านำตัวตรวจผลบิลยางทั้งหมดมาใช้แทนผลรับ–จ่าย

### 5. หลักการจัดสรรเลขท้ายและผูกเลขกับรายการ

migration `20261031020000_rubber_device_bill_numbers.sql` มี suffix counter และ number binding ที่อยู่แยกจากรายการธุรกิจ การส่งซ้ำคืนเลขเดิม และการลบรายการไม่คืนเลข แนวทางนี้ตรงกับข้อตกลงรับ–จ่าย

ข้อจำกัด: `private.allocate_rubber_bill_suffix`, `assert_rubber_bill_numbering` และ trigger `preserve_rubber_bill_number` อ้าง table และประเภทบิลยางโดยตรง ไม่ควรเรียกกับรับ–จ่ายตรง ๆ

ข้อเสนอ: ใช้ทะเบียนเครื่องร่วม แต่เพิ่มการจัดสรรและ binding ที่รองรับรับ–จ่ายโดยเฉพาะ หรือแยกแกนร่วมเมื่อพิสูจน์ได้ว่าขนาดและความซับซ้อนลดลง หากใช้ที่เก็บ binding ร่วม ต้องแยกเอกลักษณ์ตามโมดูลและ client identity อย่างชัดเจน ไม่ปะปนประวัติยางกับรับ–จ่าย การจัดสรรเลขท้ายต้องอยู่ใน transaction สร้างรายการจริงและไม่เกิดตั้งแต่รับคำขอรออนุมัติ

### 6. รูปแบบการทดสอบที่นำมาใช้ต่อได้

ใช้กรณีและเครื่องมือใน `tests/rubber-device-numbering.spec.ts`, `rubber-device-numbering-concurrency.spec.ts`, `rubber-device-numbering-browser.spec.ts` และ `supabase/tests/rubber_device_bill_numbers_test.sql` เป็นแบบสำหรับทดสอบรับ–จ่าย เพิ่มเข้า regression ออฟไลน์และ PWA ของรับ–จ่ายที่มีอยู่ ไม่ใช่คัดลอกผลผ่านเดิมมาอ้างว่ารับ–จ่ายผ่านแล้ว

กรณีสำคัญ: หลายแท็บออกเลขพร้อมกัน, I/E/ยางไม่กินลำดับกัน, ย้อนวันที่แล้วนับต่อ, transaction ล้มเหลว, ส่งซ้ำหลังขาดการตอบกลับ, ฐานซ้ำต่างรายการ, รออนุมัติแล้วอนุมัติ/ปฏิเสธ, แก้ไข/ลบแล้วไม่เปลี่ยนหรือคืนเลข, ทะเบียนเปลี่ยนแต่คิวเดิมคงฐานเดิม และอัปเกรดโดยคิวเก่าไม่เปลี่ยน

## ส่วนที่ควรแยกไว้

- **คิวกลางและคำสั่งธุรกิจ:** `src/lib/rubber-bills/central-sync.ts` ผูกกับ endpoint `/rubber-bills/queue`, รุ่นคำสั่ง สถานะคิว และการยืนยันผลของยาง ส่วน `src/lib/income-expense/background-command.ts` รองรับ update/delete รายรับ–รายจ่ายทั่วไปและมีเอกลักษณ์คำสั่งของตัวเอง การทำเลขร่วมไม่จำเป็นต้องรวมคิวธุรกิจกลาง
- **กติกาอนุมัติ:** ยางมีราคา น้ำหนัก และช่วงแก้ไข ส่วนรับ–จ่ายมีคำสำคัญ ยอดเงิน และวันที่ อ้าง `src/lib/rubber-bills/approval.ts`, `immediate-receipt.ts`, `src/hooks/useIncomeExpenseApprovals.ts` และ `src/lib/income-expense/approval-cache.ts` ใช้สถานะหรือเครื่องมือพื้นฐานร่วมได้ แต่ไม่ใช้เกณฑ์อนุมัติยางแทนรับ–จ่าย
- **การคำนวณและความสัมพันธ์ต้นทาง:** สูตรบิลยาง สต็อก การเงิน รายงาน การรับโอน และการล็อก ต้องคงตรวจตามต้นทางของแต่ละโมดูล
- **เอกสาร PDF:** มีเครื่องมือแชร์ร่วม `src/hooks/useSharePdf.ts` อยู่แล้ว แต่แบบเอกสารและสิทธิ์พิมพ์เป็นของแต่ละโมดูล การออกเลขรับ–จ่ายไม่ได้ยืนยันให้เพิ่มการพิมพ์หรือแชร์ PDF อัตโนมัติสำหรับรายรับ/รายจ่ายทั่วไป

## จุดเชื่อมต่อที่ต้องแก้ให้ครบเมื่อเริ่มพัฒนา

1. **จังหวะอนุมัติมาก่อนการบันทึกในเครื่อง:** `src/lib/income-expense/persist-submissions.ts` เรียก `approve` ก่อน `create` ในงานสร้าง และ `submitForApprovalIfNeeded` ส่งคำขอออนไลน์ก่อนเข้าเส้นทางสร้างในเครื่อง จึงต้องจัดลำดับใหม่ให้เลขฐานและเจตนาสร้างคงทนก่อนส่งคำขอ โดยไม่ส่งคำขอซ้ำหรือข้ามกติกาอนุมัติ
2. **ห้ามขยายสิทธิ์ออฟไลน์โดยอ้อม:** ปัจจุบัน `useIncomeExpenseApprovals.ts` และ `approval-cache.ts` ป้องกันรายการบางประเภทที่ต้องอนุมัติขณะออฟไลน์ การเปลี่ยนเลขไม่ได้อนุญาตให้ออฟไลน์ทำทุกกรณี หากต้องเปลี่ยนเงื่อนไขนี้ต้องถามผู้ใช้เป็นอีกการตัดสินใจ
3. **เลขจากจำนวนรายการในหน้าจอ:** `IncomeExpenseModule.tsx` ใช้ `transactions.length + 1` และ `IncomeExpenseModal.tsx` สร้างเลขในฟอร์ม ต้องเปลี่ยนไปใช้ผลจากการบันทึกจริงที่รองรับหลายแท็บ ไม่ใช้ความยาวรายการที่โหลดหรือจำนวนแถวที่เหลือหลังลบ
4. **ตัวตนแต่ละแถวเมื่อบันทึกสำเร็จบางส่วน:** ฟอร์มทั่วไปสร้าง client identity ใหม่ภายใน `filledLines.map(...)` ขณะที่ `persist-submissions.ts` บันทึกทีละแถวและอาจหยุดเมื่อแถวหนึ่งผิดพลาด ต้องทำให้แถวที่รับไว้แล้วถูกจดจำเมื่อกดลองใหม่ เพื่อไม่ออกเลขหรือสร้างซ้ำให้แถวเดิม โดยยังคงหน่วยหนึ่งแถวต่อหนึ่งรายการตามที่ยืนยัน
5. **ส่ง metadata ครบทุกทาง:** `build-income-expense-payload.ts` ยังไม่มีข้อมูลออกเลขใหม่ ต้องรักษาฐาน วันที่เดิม issuer และลำดับ ผ่านสร้าง แก้ไข ลบ คำขออนุมัติ ประวัติ และการส่งซ้ำ ไม่ให้ขั้นตอนสร้าง payload ใหม่ทำข้อมูลเลขหาย
6. **ป้องกันใช้ backend เก่าที่ไม่รองรับเลขใหม่:** บิลยางมี numbered RPC ตาม migration `20261031022000_rubber_numbered_transport_fence.sql` รับ–จ่ายปัจจุบันยังเรียก `sync_income_expense` ต้องเพิ่มการตรวจความสามารถที่ชัดเจน ไม่ยอมให้เลขใหม่กลายเป็นเลขเก่าเงียบ ๆ เมื่อ client กับ server อัปเกรดไม่พร้อมกัน และต้องครอบคลุมทั้งเส้นทางสร้างตรงกับสร้างหลังอนุมัติ
7. **การแสดงผลและข้อมูลที่อ่านกลับ:** `income-expense/operational-list.ts` แสดงฐานจากคิวได้อยู่แล้ว แต่ต้องอ่าน metadata กลับจากผลส่วนกลาง และตรวจตาราง ค้นหา หน้ารออนุมัติ รายละเอียด รายงาน และการอ้างอิงเลขเดิมให้ครบโดยไม่เปลี่ยนเลขรายการนอกขอบเขต

## ลำดับงานที่เสนอ

1. ข้อตัดสินใจหลักยืนยันครบแล้ว รวมหลายบัญชี/หลายแท็บและการเลิกใช้รหัสร่วม ตรวจ [แผนพัฒนาและเกณฑ์ตรวจรับแบบรวม](income-expense-device-numbering-design.md) และรอผู้ใช้ยืนยันแบบรวมก่อนเริ่มพัฒนา
2. ขยาย backend ให้รับ metadata เลขใหม่ จัดสรรและรักษาเลขท้าย และตรวจความสามารถ ทั้งคำขอสร้างตรงและสร้างหลังอนุมัติ โดยยังรองรับข้อมูลและคิวเดิม
3. แยกการเข้าถึงทะเบียนเครื่องร่วมเท่าที่จำเป็น เพิ่มการออกเลข I/E พร้อมคิวในเครื่อง และจัดลำดับการเก็บก่อนส่งอนุมัติให้ตรงข้อตกลง
4. ต่อผลเลขจริงเข้าฟอร์มและทุกรูปแบบการแสดง ปรับตัวตรวจผลและทางลองซิงก์ แล้วทดสอบรับ–จ่ายร่วมกับ regression บิลยาง

## ประเมินความยากและการลดขอบเขตตามคำถามผู้ใช้

ผู้ใช้ยืนยันใช้ขอบเขตเล็กและรายการตัดออกจากรอบแรกที่ระบุด้านล่างเป็นแผนหลักแล้วเมื่อ 2026-10-31 โดยคงข้อตกลงเลขบิลเดิมทั้งหมด ส่วนระดับความยากเป็นการประเมินจาก source code และจุดเชื่อมต่อ ไม่ใช่ผลจับเวลาพัฒนาหรือ benchmark การเลือกขอบเขตนี้ยังไม่ใช่การยืนยันแบบรวมเพื่อเริ่มพัฒนา

| ลำดับจากยากไปง่าย | งาน | เหตุผลและส่วนที่ลดได้ |
| --- | --- | --- |
| 1 | เลขท้ายส่วนกลางและการรักษาเลขเดิม | ต้องทำงานถูกทั้งสร้างตรง สร้างหลังอนุมัติ ส่งซ้ำ ลบ และข้อมูลเก่า พร้อมข้อบังคับและการตรวจความสามารถของ backend; จำเป็นถ้าคงแบบฐานบวกเลขท้ายที่ยืนยันแล้ว |
| 2 | ออกเลขในเครื่องพร้อมเก็บงานรอส่ง | ต้องกันหลายแท็บ ดูแลตัวตนแถวเดิมเมื่อบันทึกบางส่วนสำเร็จ และไม่กินลำดับข้ามประเภท; ลดได้โดยทำ allocator รับ–จ่ายที่เล็กและใช้ทะเบียนร่วม ไม่ย้าย allocator ยางทั้งหมดหรือสร้างระบบปลั๊กอินทั่วไป |
| 3 | เชื่อมการออกเลขเข้ากระบวนการอนุมัติเดิม | ต้องเก็บฐานและเจตนาสร้างก่อนส่งคำขอ และส่ง metadata เดิมครบทั้งทางตรงและทางอนุมัติ; ลดได้โดยปรับเฉพาะจุดเชื่อม ไม่เปลี่ยนเกณฑ์อนุมัติหรือขยายสิทธิ์ออฟไลน์ |
| 4 | ตรวจผลซิงก์ การอ่านกลับ และความเข้ากันได้กับข้อมูลเก่า | ต้องตรวจเลขฐาน–เลขท้ายครบเส้นทาง รวม retry และคงเลขเก่า/คิวเก่า; ตัดออกไม่ได้ แต่ลดงานได้ด้วยการใช้ contract และตัวซิงก์เดิมต่อ |
| 5 | ใช้ทะเบียนเครื่องร่วม | มีทะเบียน endpoint และหน้าผู้ดูแลพร้อมแล้ว; เพิ่มการเข้าถึงร่วมที่จำเป็น ไม่สร้างทะเบียนใหม่หรือเปลี่ยนชื่อ table/endpoint ทั้งระบบ |
| 6 | ช่องเลขที่บิลเดียวและข้อความสถานะ | แก้การแสดงผลตามเลขที่ได้รับจริง; ทำได้ง่ายกว่างานข้างต้น แต่ควรต่อหลังสัญญาเลขและผลซิงก์ชัดเจน |

### ขอบเขตเล็กที่แนะนำสำหรับรอบแรก

คงทะเบียนเครื่องเดิม ตัวนับ I/E แยกตามวัน การบันทึกเลขพร้อมคิว เลขท้ายและ binding หลังสร้างสำเร็จ การส่งข้อมูลเลขผ่านอนุมัติ ตัวตรวจผลทุกเส้นทาง การคงข้อมูลเก่า และช่องเลขเดียว รวมการทดสอบกติกาเหล่านี้กับ regression ยางที่เกี่ยวข้อง

ตัดออกจากรอบแรกได้โดยไม่ลดข้อตกลงเลขบิล:

- การย้ายรับ–จ่ายไปใช้คิวกลางบิลยาง หรือสร้างตัวประสานซิงก์ใหม่
- การรวมเกณฑ์อนุมัติ สูตรคำนวณ และกติกาสต็อกของสองโมดูล
- การทำระบบออกเลขทั่วไปสำหรับทุกโมดูล ย้ายที่เก็บยางทั้งหมด หรือรวม suffix/binding table ให้เป็นชุดเดียวเพียงเพื่อใช้ชื่อร่วม
- หน้าทะเบียนเครื่องใหม่ Dashboard และการปรับชื่อ table/endpoint ทั่วระบบ ใช้หน้าจัดการเดิมพร้อมปรับข้อความที่จำเป็นได้
- การเพิ่ม PDF หรือแชร์อัตโนมัติสำหรับรายรับ/รายจ่ายทั่วไป และการขยายไปบิลขาย โอนสาขา เงินเดือน หรือเปลี่ยนเลขย้อนหลัง

การตัดเลขท้ายเองเป็นการเปลี่ยนแบบที่ผู้ใช้ยืนยันแล้ว ไม่ใช่การลดงานส่วนเกิน หากเลือกทางนั้นต้องทบทวนวิธีรับมือฐานซ้ำจากการกู้หรือคัดลอกข้อมูลก่อน ไม่ควรลดการตรวจผลหรือการรักษาเลขคงเดิมแทน

### ผลที่คาดว่าจะดีขึ้นจากระบบปัจจุบัน

- เลขในเครื่องอิง counter ที่คงทน แทน `transactions.length + 1` ที่เป็นจำนวนรายการที่โหลดอยู่ในหน้าจอ; ไม่เปลี่ยนหลักการออกเลขตามรายการที่โหลด กรอง หรือลบ
- มีเลขระบุประเภท/วันที่/เครื่องที่อ้างอิงได้ตั้งแต่บันทึกในเครื่อง โดยเลขฐานคงเดิมตลอดอายุรายการ และเลขยืนยันได้เมื่อส่วนกลางสร้างสำเร็จ
- หลายแท็บจัดสรรลำดับผ่านการบันทึกที่กันการชนกัน และแต่ละชุด I/E/ยางนับแยกกัน; การล้างข้อมูลยังต้องรับทะเบียนที่ถูกต้องก่อนใช้ และฐานจากสำเนาข้อมูลอาจซ้ำได้ตามข้อจำกัดที่ยอมรับด้วยเลขท้าย
- ผู้ใช้เห็นช่องเลขเดียวและสถานะตามขั้นตอนจริง ผู้ดูแลใช้ทะเบียนเครื่องเดิมได้

ระบบปัจจุบันมีคิวออฟไลน์ การส่งซ้ำ และการตรวจบัญชี/สาขาอยู่แล้ว คุณค่าของรอบนี้คือความแน่นอนของเลขและการอ้างอิงเป็นหลัก ยังไม่มีหลักฐานว่าการเปลี่ยนนี้ทำให้ซิงก์เร็วขึ้น และไม่ได้เพิ่มความถูกต้องของยอดบัญชีโดยอัตโนมัติ ต้องพิสูจน์พฤติกรรมใหม่ด้วยการทดสอบเมื่อพัฒนาแล้ว

ตรวจครั้งนี้เป็นการอ่านและจัดทำเอกสารเท่านั้น ไม่แก้ source code, ไม่ apply migration และไม่รันทดสอบ feature ที่ยังไม่ได้พัฒนา ขณะตรวจพบการแก้ไฟล์อนุมัติรับ–จ่ายและไฟล์อื่นอยู่ก่อนแล้ว จึงไม่นำมารวมเป็นผลงานของการตรวจนี้
