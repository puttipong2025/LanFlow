# เงินเดือนและยอดรับ–จ่ายสุทธิสะสม

สถานะ: Local implemented and verified 2026-10-31; ยังไม่ apply Cloud ดู payroll-branch-balance-verification.md

## กติกาที่ยืนยัน

- ใช้โอนเงินลูกค้าเป็นต้นแบบ: เฉพาะส่วนสาขาจ่ายกระทบรับ–จ่ายสุทธิสะสม
- ส่วนโอนยังแสดงในประวัติภาพรวมและเปิดดูสลิปได้ แต่ไม่รวมในรับ–จ่ายสุทธิสะสม
- การแนบสลิปเป็นหลักฐาน ไม่สร้างรายจ่ายซ้ำ
- รายการเก่าคงการคำนวณเดิม จนกว่าจะตรวจยืนยันช่องทางจ่ายได้ ห้ามเดาหรือปรับย้อนหลังทั้งหมด

## ตัวอย่างตรวจรับ

| เงินเดือนสุทธิ | ส่วนโอน | ส่วนสาขาจ่าย | ผลต่อสุทธิสะสม |
|---:|---:|---:|---:|
| 15,000 | 15,000 | 0 | 0 |
| 15,000 | 10,000 | 5,000 | -5,000 |
| 15,000 | 0 | 15,000 | -15,000 |

การเพิ่มหลักฐานของยอดเดิมต้องไม่ทำให้ผลในตารางถูกหักซ้ำ

## หลักฐานและขอบเขตที่ต้องตรวจต่อ

- `20260812010000_dashboard_accumulated_daily_summary.sql`: ลูกค้านับ `branch_paid_amount` แต่สูตรเงินเดือนในไฟล์นี้อ่าน `net_pay` เต็มจำนวน ต้องตรวจนิยามล่าสุดก่อนสรุปว่าปัจจุบันยังเป็นเช่นนี้
- `20261009013000_time_payroll_payment_allocation.sql`: มี `time_payroll_branch_paid_amount` แยกส่วนสาขาจ่าย และใช้ในรายงานกับเหตุการณ์เงินเดือน แต่ยังสร้างเหตุการณ์ส่วนโอน `time-payroll-transfer` เพื่อประวัติ
- ต้องตามสูตรภาพรวมล่าสุด รวมยอดรายวัน ยอดสะสม การแจ้งเตือน และฐานเปรียบเทียบนับเงิน ว่าใช้ส่วนสาขาจ่ายตรงกัน
- ต้องตรวจการแก้ไข ยกเลิก และลบ ว่าย้อนผลตามส่วนที่เคยกระทบจริง และไม่ทำให้ประวัติซ้ำ
- ข้อสรุปล่าสุด: ค่าใช้จ่ายดำเนินงานสะสมนับเต็ม 15,000 แม้โอน 10,000 และสาขาจ่าย 5,000; สุทธิสะสมลดเฉพาะ 5,000 และใช้ค่าใช้จ่ายเต็มคำนวณเปอร์เซ็นต์

## ผลวิเคราะห์ 2026-10-31

ตรวจ migration และนิยามฟังก์ชันจริงใน Local `supabase_db_webapp` แบบอ่านอย่างเดียว ไม่ได้ตรวจ Cloud

1. ยืนยันช่องว่างที่ `private.calculate_dashboard_summary`: ยังอ่านเงินเบิก `ft.amount` และเงินเดือน `ps.net_pay` เต็มจำนวน แม้ต้นทางมี `payment_transfer_amount` แล้ว ทั้งรับ–จ่ายสุทธิสะสมและยอดจ่ายวันนี้จึงรวมส่วนโอนด้วย
2. ตัวอย่าง SELECT ด้วยค่าจำลอง 15,000: โอนทั้งหมดควรนับ 0; โอน 10,000 ควรนับ 5,000; สาขาจ่ายทั้งหมดนับ 15,000; legacy มีสาขานับ 15,000 ตามเดิม ฟังก์ชัน `time_payroll_branch_paid_amount` ให้ผลตามนี้แล้ว แต่ภาพรวมยังไม่เรียกใช้
3. Income/Expense operational feed, reportable items, report period rows และ payroll money source entries เรียก helper แยกส่วนแล้ว จาก migration `20261009013000_time_payroll_payment_allocation.sql` จึงมีสูตรต่างจากภาพรวม
4. ประวัติส่วนโอน `time-payroll-transfer` แสดงเมื่อ paid/overpaid และไม่ใช่ข้อมูลที่ summary นำมาบวกยอด (`calculate_dashboard_summary` ไม่อ่าน `dashboard_money_events`) ปัญหาที่พบคือ summary ใช้ยอดต้นทางเต็ม ไม่ใช่การรวม event สลิปซ้ำใน summary
5. `start_cash_count` ใน `20261024010000_independent_cash_counts.sql` ใช้ `netCashFlow` จากสูตรสดเป็น system balance; Telegram และกลุ่มแจ้งเตือนเงินใช้ค่าเดียวกันจาก snapshot จึงได้รับผลต่อเนื่อง รวมสถานะเงินของสาขาในตัวเลือกสาขา
6. คำแนะนำวิธีจ่ายใน `src/lib/time-tracking/payment-allocation.ts` อิง netCashFlow จึงอาจแนะนำยอดสาขาจ่ายต่ำเกินจริงเมื่อยอดสะสมถูกหักส่วนโอนไปด้วย
7. ตัวตั้งต้น financial_amounts เดียวกันยังคำนวณ operatingExpenseAccumulated และ operatingBurdenPercent ด้วย การแทน amount ทั้งก้อนจะเปลี่ยนสองค่านี้ตามไปด้วย ต้องแยกจำนวนที่กระทบยอดเงินจริงจากจำนวนที่ใช้รายงานต้นทุน ผู้ใช้ยืนยันให้รักษาต้นทุนเต็ม 15,000 โดยแยกยอดเงินจริงสาขา 5,000
8. Memory `50_Wiki/LanFlow/LanFlow_Time_Payroll_Payment_Allocation.md` ระบุว่า Dashboard ใช้ branch portion แล้ว แต่ขัดกับนิยาม Local ที่ตรวจพบ จึงยึดโค้ดและฐานข้อมูลเป็นหลัก

### ขอบเขตแนะนำเมื่อเริ่ม implementation

- เพิ่ม migration แก้ summary สำหรับเงินเบิกและเงินเดือนโดยใช้ helper เดิมเพื่อรักษา legacy ไม่แก้ migration เก่า
- แยก balance amount จาก operating expense amount เพื่อไม่เปลี่ยนรายงานต้นทุนโดยไม่ได้รับข้อสรุป
- คงประวัติและสลิปส่วนโอนเดิม; ไม่แก้ business rows หรือผลนับเงินเก่าที่บันทึกแล้ว
- หลังแก้ให้คำนวณ dashboard snapshot ใหม่ของสาขาที่เกี่ยวข้อง; การ invalidate หน้าเว็บอย่างเดียวไม่แก้สูตรฐานข้อมูล
- เพิ่มการตรวจ summary เทียบส่วนสาขาจ่าย ครบโอนทั้งหมด/แบ่งจ่าย/สาขาจ่ายทั้งหมด/legacy/จ่ายนอกระบบ รวมแนบสลิป แก้ ยกเลิก ลบ และการเริ่มนับเงินครั้งใหม่
- รอบนี้ตรวจด้วย SELECT ค่าจำลองและอ่านนิยามจริง ไม่ได้รัน mutation หรือชุดทดสอบเขียนข้อมูล
