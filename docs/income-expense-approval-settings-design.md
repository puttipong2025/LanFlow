# การออกแบบหน้าตั้งค่าและอนุมัติรับ–จ่าย

สถานะ: ผู้ใช้สั่งเริ่มงานแล้ว ดำเนินการและตรวจใน local วันที่ 2026-10-31 ไม่รวม Cloud deployment

## ข้อสรุปที่ผู้ใช้ยืนยัน

- ปรับหน้าจอและฟอร์มตั้งค่าและอนุมัติรับ–จ่ายให้สวยงามและตอบสนองผู้ใช้
- ใช้สิทธิ์แก้ไขเช่นเดียวกับราคายางที่กำหนดสูงสุด: เฉพาะ Super Admin แก้ไขได้ ผู้จัดการระบบอ่านค่าได้
- สิทธิ์นี้ครอบคลุมทั้งเกณฑ์ยอดเงิน ข้อความที่ต้องขออนุมัติ กฎวันที่รับ–จ่าย และกฎขออนุมัติก่อนลบรายการโยกเงินที่ปลายทางรับแล้ว ผู้ใช้ยืนยันคำตอบ “1 และ 2”
- คำขออนุมัติอยู่ด้านบน ส่วนการตั้งค่าอยู่ด้านล่างและเริ่มต้นพับไว้ เปิดด้วยปุ่ม “ตั้งค่าระบบ” ฟอร์มตั้งค่าเรียงแนวตั้งและรองรับมือถือ ผู้ใช้เลือกแบบที่ 1
- คงสิทธิ์อนุมัติและปฏิเสธคำขอรายรายการตามเดิม การจำกัดเฉพาะ Super Admin ใช้กับการแก้กติกาเท่านั้น ผู้ใช้เลือกแบบที่ 1
- แยกปุ่มบันทึกเกณฑ์ยอดเงิน กฎวันที่ และกฎลบโยกเงินออกจากกัน ส่วนข้อความมีปุ่มเพิ่มและปิดใช้งานของตัวเอง ผู้ใช้เลือกแบบที่ 1
- ข้อสรุปล่าสุด: ผู้ใช้เปลี่ยนจากการ์ดเป็นตารางทุกขนาดหน้าจอ เพื่อเห็นหลายแถวในพื้นที่เดียว ยอมรับการเลื่อนแนวนอนบนมือถือ และให้จัดคอลัมน์คล้ายตารางเดิม (แทนข้อสรุปการ์ดก่อนหน้า)

## แนวทางประกอบที่เสนอ

- เมื่อพับ/เปิดการตั้งค่าระหว่างใช้งานหน้าต่างเดิม ให้เก็บค่าที่กำลังกรอกไว้
- การบันทึกแต่ละส่วนต้องส่งเฉพาะค่าของส่วนนั้น เพื่อไม่ให้บันทึกค่าร่างหรือเขียนทับส่วนอื่นโดยไม่ตั้งใจ
- ใช้การ์ดฟอร์มและองค์ประกอบเดิมของโปรเจกต์ โดยคงเงื่อนไขตรวจยอดเงิน ข้อความ วันที่ และขั้นตอนพิจารณาคำขอเดิม
- จำกัดสิทธิ์การแก้กติกาทั้งหน้าจอและฐานข้อมูล การซ่อนปุ่มเพียงอย่างเดียวไม่เพียงพอ

## ข้อกำหนดหลังตรวจแผนกับโปรเจกต์

- เพิ่ม forward migration แยกสิทธิ์อ่านและเขียนของ settings/keywords เฉพาะจุด เพราะนโยบายเดิมใช้ `FOR ALL` คงสิทธิ์ผู้จัดการระบบในการอ่านข้อความทั้งเปิดและปิดใช้งาน พร้อมจำกัดการเขียนเฉพาะ active Super Admin ไม่เปลี่ยน helper สิทธิ์กลางหรือสิทธิ์พิจารณาคำขอ
- บันทึกเฉพาะค่าของแต่ละส่วนและตรวจค่าก่อนหน้าแบบ atomic ที่ฐานข้อมูล การแก้ส่วนเดียวกันจากอีกเครื่องต้องแจ้งขัดแย้งให้ตรวจค่าล่าสุด การแก้คนละส่วนไม่ควรชนเพราะเวลาแก้ไขกลางของทั้งแถว
- ยืนยันผลแถวที่บันทึกจริงก่อนแจ้งสำเร็จ กรณีศูนย์แถว ข้อมูลหาย หรือผลไม่ตรงต้องแจ้งปัญหา การปิดข้อความต้องตรวจผลเป้าหมายด้วย
- แยกค่าร่าง ค่าที่บันทึกแล้ว และสถานะโหลด/บันทึก/error ของแต่ละส่วน การ refetch หรือบันทึกส่วนอื่นต้องไม่ล้างร่าง มีปุ่มลองใหม่เมื่อโหลด settings/keywords ไม่สำเร็จ และปิดการเขียนเฉพาะส่วนที่ยังไม่มีข้อมูลที่เชื่อถือได้
- การพับ UI ไม่หยุดการโหลดกติกาที่หน้ารับ–จ่ายใช้ร่วมกันหรือการอัปเดต cache วันที่สำหรับออฟไลน์ แสดงว่าการตั้งค่ามีผลทุกสาขาและตัวกรองสาขากรองเฉพาะคำขอ
- ใช้เส้นทาง Supabase/hook และ handler ตัดสินเดิมเป็นจุดเริ่มต้น แยกส่วนตั้งค่า/ตารางคำขอเพื่อผ่านเพดานขนาดไฟล์โดยไม่เพิ่ม baseline และไม่สร้าง API ใหม่ทุกส่วนหากเส้นทางเดิมรองรับสัญญาครบ
- ปรับ selectors ของ browser tests เดิมเฉพาะส่วนแสดงคำขอ คง assertion ธุรกิจเดิม และรัน browser tests แยกจาก `npm run verify` พร้อมตรวจ RLS ด้วยบทบาทผู้ใช้จริง

### ข้อกำหนดจาก scrutinize รอบสอง

- ใช้ mutation settings เดียวที่รับชนิดส่วนจำกัด 3 แบบพร้อมค่าที่ต้องการและค่าก่อนหน้า แปลงเป็นคอลัมน์ที่อนุญาตภายใน ไม่สร้าง API/hook แยกทุกส่วนหากเส้นทางเดิมรองรับ และไม่รับชื่อคอลัมน์ทั่วไปจากฟอร์ม
- คงสิทธิ์เปิดหน้าต่างและพิจารณาคำขอของผู้จัดการตามเดิม ส่งความสามารถแก้กติกาจาก parent ที่มี profile อยู่แล้วแยกจาก guard ของทั้งหน้าต่าง
- ตรวจออนไลน์ทั้ง UI และก่อนเริ่ม mutation ตั้งค่า/ข้อความ ใช้ connectivity guard และ networkMode เฉพาะจุดตามตัวอย่างบิลยาง เมื่อเปิดหน้าแล้วเน็ตหลุดให้เก็บร่าง ปิดปุ่มเขียน และแจ้งทันที ไม่พักงานไว้ส่งเมื่อกลับออนไลน์หรือรอ refetch ที่หยุดออฟไลน์ในเส้นทาง error
- แยก loading ของ settings/keywords ออกจากคำขอจริง การตั้งค่าโหลดช้าหรือล้มเหลวต้องไม่บังรายการที่โหลดได้แล้ว
- รวมผลบันทึกลง cache/ฐานค่าร่างเฉพาะส่วนที่ยืนยัน ไม่แทน settings ทั้งแถวด้วยคำตอบที่อาจเก่ากว่าส่วนอื่น ทดสอบผลตอบกลับสลับลำดับให้ค่ากฎวันที่และ cache ออฟไลน์ไม่ถอยกลับ
- แยกผลยืนยันเขียนสำเร็จ ผลปฏิเสธ และผลที่ยังยืนยันไม่ได้ หากส่งคำสั่งแล้วคำตอบหายต้องตรวจข้อมูลจริงเมื่อเชื่อมต่อได้ ไม่แจ้งล้มเหลวแน่นอนหรือส่งเพิ่มข้อความซ้ำอัตโนมัติ; หากยืนยันเขียนแล้วแต่ refresh ล้มเหลวให้แจ้งสองผลแยกกัน
- SQL tests ใช้ transaction/rollback และ browser tests ที่แตะ singleton settings คืนค่าใน finally พร้อมรันกลุ่มที่แตะค่ากลางเรียงกัน รักษางานอื่นที่กำลังแก้ใน checkout

## แผนดำเนินงานฉบับปรับปรุง

เช็กลิสต์ความคืบหน้าหลักอยู่ใน Vault `codingDO` ที่ `10_Daily/2026-10-31.md` หัวข้อ “แผนดำเนินงาน — ปรับหน้าตั้งค่าและอนุมัติรับ–จ่าย” โดยรวม 6 Phase เดิมเหลือ 4 Phase:

1. ตรวจเส้นทางเดิมและกำหนดสัญญาสิทธิ์/การบันทึก
2. ปรับฐานข้อมูล การบันทึก ฟอร์ม และการ์ด พร้อมตรวจเฉพาะส่วนระหว่างทำ
3. ตรวจการทำงานร่วมกันและชุดตรวจรวม รวม browser tests, database tests และ `npm run verify`
4. อัปเดตเอกสารและส่งมอบหลักฐาน

อัปเดต checkbox ระหว่างทุก Phase เมื่อทำและตรวจยืนยันแล้ว ใช้ Daily เป็นแหล่งความคืบหน้าหลัก ส่วนข้อเสนอจากการสัมภาษณ์ข้างต้นใช้ประกอบเหตุผลการออกแบบ

## ประเมินความซับซ้อน

ระดับกลาง: การแสดงคำขอเป็นการ์ดทุกขนาดหน้าจอเป็นการเปลี่ยนการนำเสนอข้อมูลเดิม จุดที่ต้องระวังคือการแยกบันทึกค่าซึ่งปัจจุบันใช้การบันทึกร่วมกัน การบังคับสิทธิ์แก้กติกาที่ฐานข้อมูล และการคงขั้นตอนพิจารณาคำขอทั้งรับ–จ่าย ลบโยกเงิน และลบโอนเข้าบัญชีสาขา

## สถานะการดำเนินงาน

ผู้ใช้สั่ง “เริ่มแผนได้” และให้ดำเนินการต่อแล้ว ผลดำเนินการอยู่ด้านล่าง ไม่ commit/push หรือเปลี่ยน Cloud ในงานนี้

บันทึกนี้เก็บข้อสรุประหว่างการสัมภาษณ์ การสร้าง ADR จะพิจารณาเมื่อมีการตัดสินใจที่เปลี่ยนกลับยาก มีทางเลือกจริง และจำเป็นต้องอธิบายเหตุผลแก่ผู้ดูแลภายหลัง

## ผลดำเนินการใน local

- คำขอรับ–จ่าย ลบโยกเงิน และลบโอนเข้าบัญชีสาขาแสดงใน `IncomeExpenseApprovalTable.tsx` ทุกขนาดหน้าจอ คง native modal, AlertDialog, handler และสิทธิ์พิจารณาเดิม
- ลำดับคอลัมน์เดิม: จัดการ → รายการ → จำนวนเงิน → วันที่ → สถานะ → ผู้ขอ → ผู้พิจารณา → เหตุผล; สาขา/ประเภท/การทำรายการอยู่ใต้คอลัมน์รายการ เงินสองตำแหน่งชิดขวา ปุ่มไอคอนมีชื่อสำหรับโปรแกรมอ่านหน้าจอและพื้นที่กด 44px; ตารางใช้ความกว้างคอลัมน์คงที่ รวม 1088px บนมือถือ / 1328px ตั้งแต่ 640px อยู่ในพื้นที่เลื่อนแนวนอนที่ focus/ใช้คีย์บอร์ดได้; 3 คอลัมน์แรกบนมือถือกว้างรวม 272px (จัดการ48 / รายการ128 / จำนวนเงิน96) ทำให้เห็นยอดเงินครบที่จอ 320px ขึ้นไปโดยไม่ต้องเลื่อน หน้าต่างมือถือเต็มจอและไม่มี overflow ออกนอกหน้าต่าง
- ฟอร์มตั้งค่าเริ่มพับ เปิดด้วย “ตั้งค่าระบบ” ทุกกฎเป็นของทั้งระบบ แยกบันทึกยอดเงิน วันที่ และการลบโยกเงิน; ข้อความเพิ่ม/ปิดแยกกันและแสดงทั้งใช้งาน/ปิดใช้งาน
- ใช้ mutation settings เดียวแบบ discriminated union ผ่าน `approval-settings-mutations.ts` การเขียนแบบ compare-and-set ใช้ expected values ของส่วนเป้าหมายใน WHERE ของ PostgreSQL โดยไม่มี read-then-write แยก transaction และไม่มี API/RPC ใหม่
- ตรวจผลแถวที่ฐานข้อมูลตอบกลับและรวม cache เฉพาะส่วนที่บันทึก ป้องกันร่างหายเมื่ออ่านค่าใหม่หรือบันทึกอีกส่วน ไม่ใช้ข้อมูลอีกส่วนจากคำตอบเก่ามาทับค่าล่าสุด
- แยก loading/error/retry ของ settings/keywords จากคำขอ เก็บร่างเมื่อออฟไลน์และไม่พักคำสั่งไว้ส่งภายหลัง คำตอบสูญหายแสดงยังยืนยันผลไม่ได้และต้องโหลดล่าสุดก่อนทำต่อ
- จำกัด active Super Admin ที่ UI และ RLS พร้อมคงการอ่านของผู้จัดการรวมข้อความที่ปิด และคงเส้นทางพิจารณาคำขอเดิม
- `20261031042000_income_expense_approval_settings_access.sql` แยก policies และเพิ่ม database updated_at; `20261031043000_income_expense_keyword_disable_timestamp.sql` เพิ่ม trigger เก็บ deleted_at เมื่อปิดข้อความ ทั้งสอง migration ใช้ใน local แล้วและ snapshot `supabase-schema.sql` ตรง local หลังปรับ whitespace
- แก้จังหวะ focus คำขอจาก `initialRequestId` ให้ติดตามความพร้อมของคำขอด้วย รวมกรณีข้อมูลรายละเอียดมาก่อน count query
- หน้าต่างและ hook เหลือต่ำกว่า 500 บรรทัด นำออกจาก grandfathered source-size list; ลบ `BranchTransferDeleteApprovalRow.tsx` ที่ถูกแทนด้วยตารางรวมและไม่มีผู้เรียกแล้ว
