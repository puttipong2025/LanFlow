# รีเซ็ตรหัสเครื่องทั้งหมดโดยไม่วนใช้รหัสเดิม

> ข้อตกลงเดิมถูกแทนที่ด้วย [ADR0102](0102-clear-device-registry-and-reuse-device-codes.md) เมื่อ 2026-11-02: reset ใหม่ล้างทะเบียนรวมรหัสที่เลิกใช้ เริ่ม D01/0001 ใหม่ และรักษาเลขบิลเต็มด้วยเลขท้ายต่อ เนื้อหาด้านล่างเป็นหลักฐานการตัดสินใจเดิม

ผู้ใช้ยืนยันเมื่อ 2026-11-01 ให้ “รีเซ็ตทั้งหมด” ในหน้าเครื่องออกบิลหมายถึงเลิกใช้รหัสเครื่องที่ใช้งานอยู่ทั้งหมดทุกสาขา แล้วให้เครื่องรับรหัสใหม่ต่อจากเลขล่าสุดเมื่อกลับมาติดต่อส่วนกลาง โดยเก็บเลขบิลเดิมและงานค้างไว้ ไม่เริ่มทะเบียนใหม่จาก D01 และไม่เริ่มลำดับบิลใหม่ใต้รหัสเครื่องเดิม เพื่อรักษาการอ้างอิงเลขที่ออกแล้วและงานออฟไลน์ตาม [ADR0096](0096-branch-independent-bill-device-identity.md)

ผู้ใช้ยืนยันเพิ่มเติมให้เฉพาะ Super Admin ใช้คำสั่งรีเซ็ตทั้งหมดได้ เนื่องจากมีผลทุกสาขา ต่างจากสิทธิ์เลิกใช้รหัสรายเครื่องเดิม ก่อนดำเนินการต้องแสดงจำนวนเครื่องที่จะได้รับผล และให้พิมพ์ “รีเซ็ตทั้งหมด” ก่อนกดยืนยัน

ผู้ใช้ยืนยันว่า หากรายชื่อเครื่องที่ใช้งานอยู่เปลี่ยนระหว่างเปิดหน้าต่างยืนยันกับดำเนินการ ต้องไม่รีเซ็ตตามคำยืนยันเดิม ให้แจ้งว่ารายชื่อเปลี่ยน แสดงจำนวนล่าสุด และให้ยืนยันใหม่ เช่น เปิดไว้ตอนมี 10 เครื่องแล้วมีเครื่องที่ 11 ลงทะเบียนเข้ามา การตรวจนี้อิงชุดเครื่อง ไม่ใช่เปรียบเทียบจำนวนเพียงอย่างเดียว

สรุปขอบเขตปุ่ม: ใช้กับรหัสเครื่องที่ใช้งานอยู่ทั้งหมดทุกสาขา โดยไม่จำกัดตามตัวกรองหรือหน้าตารางปัจจุบัน หนึ่งรหัสเครื่องที่ใช้หลายสาขานับเป็นหนึ่งเครื่อง มีผลร่วมกับบิลยางและรับ–จ่ายตามทะเบียนเครื่องร่วมเดิม เครื่องออฟไลน์รับรู้การเลิกใช้เมื่อกลับมาติดต่อส่วนกลาง และบิลหรืองานค้างที่ออกเลขแล้วคงเลขเดิม

สถานะ: ผู้ใช้ยืนยันและสั่งทำครบทุก Phase เมื่อ 2026-11-01 พัฒนาและตรวจใน Local แล้ว แผน/checkbox อยู่ vault codingDO `10_Daily/2026-11-01.md` และหลักฐานอยู่ [verification ledger](../bill-device-reset-verification.md) ยังไม่ได้รีเซ็ตทะเบียนที่ใช้งานจริงหรือดำเนินการ Cloud/commit/push/deploy

## สัญญา implementation

Preview ใช้ active device UUIDs ใน `private.bill_issuer_devices` รวมเครื่องที่ไม่มี branch link และคืน count กับ SHA-256 ของชุด UUID ที่เรียงแน่นอน การติดต่อซ้ำ เปลี่ยนผู้ใช้ล่าสุด หรือเพิ่มสาขาใต้ device เดิมไม่เปลี่ยน snapshot; การเปลี่ยนตัวตนแม้จำนวนเท่าเดิมทำให้ต้องยืนยันใหม่

Route ใหม่ใช้ `requireRole(...,["super_admin"])` และ RPC ตรวจ active profile/role ซ้ำ ใช้ shared advisory gate สำหรับ register/retire เดิม และ exclusive gate สำหรับ bulk reset ก่อนตรวจชุดและ update แบบ atomic กำหนด lock timeout 3 วินาที งานอื่นจึงยังลงทะเบียนพร้อมกันได้ตาม per-installation lock เดิม

หนึ่ง request UUID ผูกผู้สั่งและ snapshot เก็บ receipt สำเร็จในธุรกรรมเดียวกับ retire ตรวจ receipt ก่อนตรวจ snapshot ของปัจจุบันเพื่อให้ retry หลัง response หายคืนผลเดิมและไม่ retire replacement codes ที่ออกแล้ว UI เก็บคำสั่งเดิมระหว่างผลไม่ชัดเจนและเปิดตรวจซ้ำได้จาก dialog เดิม ส่วน conflict ล้างข้อความยืนยันและโหลด preview ใหม่

ใช้ forward migrations `20261101040000_bill_device_bulk_reset.sql` แล้ว `20261101041000_bill_device_reset_business_conflict.sql` คู่กัน ตัวหลังแก้ business conflict เป็น `PT409`; ห้ามเปิดใช้ UI หลังลงเพียง 040000 เพราะ SQLSTATE `40001` เดิมกระตุ้น PostgREST 14 retry loop ผลตรวจจริงครอบคลุม SQL, Route, concurrency และ production PWA รวมงานเก่าที่รออนุมัติหลัง reset

เครื่องออนไลน์ก็รับรู้การเลิกใช้เมื่อการตรวจทะเบียนครั้งถัดไปสำเร็จ มี cache 60 วินาทีและการพักแท็บตามระบบเดิม ไม่รับประกันเปลี่ยนทันทีและไม่เพิ่ม realtime/คิว/IndexedDB store ใหม่ ผลสำเร็จจึงบอกจำนวนรหัสเดิมที่เลิกใช้ ไม่ยืนยันว่าทะเบียน active ต้องว่างหลังจบ

## Rollout และ rollback

ลงทะเบียนร่วม ADR0095–0097 และ forward migrations 040000/041000 ก่อนอัปเดต UI จากนั้นอ่าน preview เพื่อตรวจ readiness โดยไม่กด reset อัตโนมัติ ไม่เปิดสิทธิ์ SQL กับ private receipt ให้ client และไม่ส่งคำสั่ง reset เข้า business queue

หาก rollback UI ให้เก็บทะเบียน, shared/exclusive gate, global counter, receipts และ references เดิมไว้; ไม่ชุบรหัสที่เลิกใช้หรือลบ receipt อัตโนมัติ Receipt เก็บต่อเนื่องโดยไม่เข้า cleanup ประวัติธุรกิจทั่วไป การลด retention ของ receipt เป็นงานตัดสินใจแยก การรีเซ็ตที่ตรวจจริงอยู่ในฐานทดสอบเฉพาะ `lanflow-bill-reset-test` เท่านั้น
