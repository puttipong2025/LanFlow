# Allow deletion of an unreported withdrawal adjustment independently of its reported source

The user confirmed that a Report Lock on the original withdrawal alone must not prevent deletion of an adjustment. Delete the adjustment and its paired income/expense effect together and restore the withdrawal total, while preserving the original withdrawal and its historical reports. If the adjustment or its paired income/expense effect is included in a report, refuse deletion and show the report number and reason; this preserves reported facts without making every correction permanent merely because its source was reported.

For successive approved adjustments, deletion must proceed from the latest adjustment backward. For example, after 1,000 → 1,500 → 1,200, deleting the latest correction restores 1,500 before the earlier correction can be deleted. An adjustment already included in a report stops this sequence; deletion cannot skip it to remove an earlier correction. This avoids silently changing the basis and paired cash effects of later corrections.

Deletion follows the existing withdrawal rules for permissions, employee/branch scope, and payroll closure. A pending or approved Payroll Slip that used the adjusted balance blocks deletion until its month is reopened through the existing workflow; show the blocking month and slip identifier. Do not rewrite a closed slip automatically or block deletion solely because an unrelated older slip exists. The user explicitly confirmed reuse of withdrawal rules rather than a separate adjustment deletion policy.

Offer “จ่ายนอกระบบ” in the adjustment settlement dropdown for both increases and decreases. It changes the effective withdrawal total and payroll deductions normally, but creates no branch income/expense: an increase is paid outside the system, and a decrease is returned outside the system. Preserve the adjustment history and settlement method for inspection. This is an explicit exception to ADR 0070's requirement that every approved correction has a branch cash effect.

A subsequent pending adjustment request blocks deletion of the latest approved correction because the request depends on its balance. Require withdrawal or rejection of that request first; never cancel it automatically. The delete button appears only on the latest approved adjustment, subject to the existing withdrawal permissions; earlier corrections remain visible as history without a delete button. A rejected request does not become the latest effective adjustment.

After a successful deletion, the delete button moves to the previous approved correction, which is now the latest effective adjustment. Recheck all deletion constraints for that newly latest correction. If the deletion fails, the button stays on the unchanged latest correction; when no approved corrections remain, there is no adjustment delete button.

This revises ADR 0070's blanket prohibition on deleting approved adjustments and its mandatory branch-settlement rule.
