# เป้าโบนัสอัตโนมัติจาก REX อ้างอิงทั้งระบบ

สถานะ: ผู้ใช้ยืนยันข้อตกลงและสั่งดำเนินงานตามแผน `10_Daily/2026-11-12 2` แล้ว ตรวจ Local ครบและสั่ง push main/Supabase DB push แยกแล้ว ลง Cloud `20261112020000_branch_bonus_reference_targets.sql` สำเร็จ 2026-11-12 หลักฐาน backup/catalog/roles อยู่ใน verification และผล CI/deployment อยู่ใน Daily 2

เป้าอายุยางและน้ำหนักลดลงเปลี่ยนจากค่ากรอกเองเป็นค่าเฉลี่ยถ่วงตามน้ำหนักต้นทางของ REX ที่เข้าประวัติและลดลงมากกว่า 0% ในช่วงเดียวกันทุกสาขาที่รวมไว้ รวมใบที่เคยทำโบนัสแล้วเป็นข้อมูลอ้างอิงได้ ยกเว้น A → A โดยไม่รวมสาขาอื่นเป็นฐานเงินโบนัส ผู้ใช้เลือกละเว้นทั้งสาขา ใช้ชุดเดียวกันทุกช่วง สาขาที่มี REX ยังไม่เข้าประวัติในช่วงจริงถูกกันออก แต่ยังเห็นชื่อ/เหตุผลและช่อง disabled ไม่ต้องนับจำนวนค้าง

ใช้เป้าจากค่าก่อนปัดแทนการปัดก่อนจัดระดับคะแนน เพื่อรักษาเส้นแบ่ง ±5%/±20% และเก็บหลักฐานอ้างอิงกับผล v4 ไม่คำนวณเติมในผลเก่า เปลี่ยนข้อมูลก่อนยืนยันต้องตรวจผลใหม่ แทนการตรึง draft ตั้งแต่ครั้งแรกซึ่งต้องมีสถานะเก็บรักษาและเพิ่มความซับซ้อน

ข้อมูลอ้างอิงอ่านจาก STABLE statement snapshot ครั้งเดียวต่อ batch และใช้ context เดียวกันทุกช่วง ส่วนการเขียนยังใช้ own-branch report lock เดิม แทนการเพิ่ม lock ทุกสาขาซึ่งเสี่ยงลำดับ lock ขัดกันและเพิ่มการรอในงานอื่น การยืนยันยอมรับข้อมูล ณ จุด capture ที่ชัดเจน: commits ก่อนจุดนั้นต้องตรวจพบ ส่วน commits หลัง capture ไม่เปลี่ยน context ระหว่างบันทึกผล Tests พิสูจน์ทั้งสองฝั่งของจุดเวลาและการยืนยันสองสาขาพร้อมกัน

แยก page fingerprint ของหลักฐานต้นทางออกจาก fingerprint ยืนยันที่รวม benchmark แทนการส่งทั้ง batch ไปคำนวณใหม่ทุกหน้ารายการ จึงยังตรวจข้อมูลค่าใช้จ่ายเปลี่ยนได้ แต่การเลือกสาขาไม่ทำให้ต้องโหลด/พับรายการเดิมใหม่ คง RPC signatures และ exact receipt replay เดิมเพื่อกู้ผลที่เคย commit ได้

ขอบเขตไม่รวมตาราง cache/draft งานเบื้องหลัง การจำสาขาข้ามครั้ง หรือการแบ่งน้ำหนักบิลรับจากสาขาภายใน REX ผสม ดู [สัญญา](../branch-bonus-contract.md) และ [หลักฐาน](../branch-bonus-verification.md)
