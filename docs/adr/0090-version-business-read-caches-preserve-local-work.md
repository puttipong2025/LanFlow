# แทนที่แคชบิลยางและรับ–จ่ายตามเวอร์ชันโดยรักษางานค้าง

แคชสำหรับอ่านข้อมูลอาจเก่า แต่ข้อมูลในเครื่องยังมีงานของผู้ใช้และหลักฐานป้องกันการทำซ้ำ จึงไม่ใช้การล้างข้อมูลเว็บไซต์ทั้งชุดเป็นกลไกอัตโนมัติ ใช้ตัวตรวจร่วมอ่านเวอร์ชันแยกบิลยางและรับ–จ่ายเมื่อเปิดหน้า/F5 ขณะออนไลน์ หรือเมื่อกลับมาออนไลน์เสมอ และเพิ่มรอบตรวจค่ากลาง 10–120 นาทีได้โดย superadmin (ค่าเริ่มต้นปิด) ไม่ผูกการล้างกับทุก deployment

ใช้ขั้นตอนต่างกันตามที่เก็บข้อมูลจริง: บิลยางตรวจสำเนาตาม ID เป็นชุดก่อนเปลี่ยนข้อมูลพร้อม metadata อย่างสอดคล้องในขอบเขตสาขาที่ใช้เก็บร่วมกัน ส่วนสถานะสิทธิ์ยังแยกตามบัญชี รับ–จ่ายใช้การโหลดและ query cache เดิมโดยไม่เพิ่มประวัติ IndexedDB ใหม่ หากไม่สำเร็จให้ใช้ข้อมูลเดิม ไม่ถือว่าการไม่พบบิลในหน้าแรกคือหลักฐานลบ

คงงานที่ยังไม่ส่ง ส่งแล้วไม่ทราบผล ล้มเหลว ข้อมูลขัดแย้ง และรออนุมัติ รวมถึงหลักฐานลบและผลคำสั่งที่จำเป็น กติกานี้กำกับการล้างแคช ไม่เปลี่ยนการยืนยันผลและการจัดการคำสั่งเดิมของแต่ละโมดูล คงพฤติกรรมฉบับร่างเดิม รอผู้ใช้บันทึกหรือปิดฟอร์มก่อนเปลี่ยนข้อมูลที่กระทบฟอร์ม และให้ระบบประสานหลายแท็บเพื่อกันผู้เขียนข้อมูลรุ่นเก่า

เมื่อปิดรอบตรวจ เครื่องที่ออนไลน์และเปิดหน้าค้างจะรอโหลดหน้าใหม่หรือกลับมาออนไลน์ หากเปิดรอบให้ตรวจเฉพาะแท็บที่มองเห็นและออนไลน์ โดยเริ่มนับรอบเต็มใหม่เมื่อกลับเข้าแท็บ สถานะแคชใช้แบบรายละเอียดแยกส่วนภายในกรอบความพร้อมออฟไลน์เดิม โดยไม่ถือว่าไฟล์เว็บพร้อมออฟไลน์หมายถึงข้อมูลธุรกิจล่าสุด

ข้อตกลงนี้มี implementation และหลักฐาน local แล้ว แต่ยังไม่ยืนยันการเผยแพร่ ดู[แผนและเกณฑ์ตรวจรับ](../automatic-cache-refresh-plan.md) และ[ผลตรวจ](../automatic-cache-refresh-verification.md)

## รายละเอียดหลัง scrutinize วันที่ 2026-10-30

การอัปเกรดแคชไม่ทดแทนการแก้อาการบิลที่ลบแล้วกลับมา เพราะสถานะบิลเปลี่ยนได้โดยเวอร์ชันแคชไม่เปลี่ยน ตรวจต้นเหตุและตรึง batch/transaction รวม compatibility ของแท็บโค้ดเก่าและ rollback ก่อนเขียนโค้ด ไม่ถือว่าการเพิ่มตัวตรวจเฉพาะโค้ดใหม่ป้องกันตัวเขียนรุ่นเก่าได้แล้ว ประสาน reconnect reload เดิมกับกติกาฟอร์มและการซิงก์ผ่านเจ้าของการตรวจแคชจุดเดียว แผนดำเนินงานลดเหลือ 4 Phase โดยทดสอบและปรับเอกสารระหว่างทำ ผู้ใช้สั่งเริ่มและดำเนินงานใน local แล้วในวันที่ 2026-10-30

## สัญญาที่ตรวจยืนยันระหว่างพัฒนา

ใช้ protocol1แยกจากrepair counterเพื่อให้แอปที่เปิดอยู่รับcounterที่เพิ่มขึ้นได้ หากformatไม่รองรับจึงให้โหลดแอปใหม่ ไม่รับcounterย้อนหลัง IndexedDB7→8เพิ่มbusiness_cache_metaโดยรักษาข้อมูลเดิมและfenceตัวเขียน7; rollbackต้องรักษาopener8 ไม่ล้างฐานข้อมูล

การอ่านtableตรงไม่ผ่านcolumn grantsและไม่ให้derived lock/approvalครบ จึงเพิ่มmigration `20261030030000_business_cache_receipts.sql` สำหรับbounded read RPCที่ตรวจrole/browser-session/locationชัดเจน ล็อกsearch_pathว่างและตัดprivate OCR provenance ไม่เพิ่มสิทธิ์table ไม่ใช้service-role ไม่มีCloudapplyในรอบนี้

## ค่ากลางสำหรับรอบตรวจ (ต่อยอด 2026-10-30)

`business_cache_settings` เก็บ interval_minutes nullable (ปิด) หรือจำนวนเต็ม 10–120 กับ revision; เฉพาะ super_admin ที่ active และผ่าน session gate เขียนผ่าน save_business_cache_settings ได้ ไม่ใช้สิทธิ์ delegated manager การแก้พร้อมกันคืน 409 ให้เปิดอ่านใหม่ ค่าเริ่มต้นปิดเพื่อรักษาพฤติกรรมเดิม

แต่ละเครื่องรับค่าจาก metadata ตอนเปิด/F5/กลับออนไลน์/รอบเดิม ไม่มีช่องทาง push เพิ่ม เมื่อเครื่องปิดรอบอยู่ต้องเปิดหน้าใหม่หรือกลับออนไลน์จึงทราบค่าที่เครื่องอื่นเปิด ตัวตั้งเวลาหยุดเมื่อ offline/hidden และถอดเมื่อออกจาก scope การตรวจและรอฟอร์มยังใช้เจ้าของเดิม ไม่ล้างคิวหรือ draft ช่องนาทีใช้ NumberField เดิมจึงมี zero focus/blur เหมือนบิลยาง
