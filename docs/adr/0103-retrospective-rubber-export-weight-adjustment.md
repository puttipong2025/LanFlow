# ปรับน้ำหนักส่งออกยางย้อนหลังโดยใช้สิทธิ์จัดการเดิม

ให้ผู้ใช้กรอกเปอร์เซ็นต์น้ำหนักลดลงหรือน้ำหนักปัจจุบันของรายการส่งออกยางย้อนหลังได้ โดยลดผลกระทบต่อโมดูลอื่น การย้อนรายการที่ตรวจสอบแล้วเป็นฉบับร่างอาจติดรายงานของรายการโอนค่าทำงาน และล้างข้อมูลการเงินกับสลิป จึงแยกการปรับน้ำหนักออกจากการย้อนสถานะรายการ

## ข้อตกลงที่ผู้ใช้ยืนยันแล้ว

- ผู้ใช้เป็นผู้กรอกเปอร์เซ็นต์เอง ไม่ใช่การกำหนดเปอร์เซ็นต์ตายตัวหรือสั่งแก้ข้อมูล Cloud รายรายการในขั้นออกแบบ
- เปอร์เซ็นต์หมายถึงน้ำหนักที่ลดลง โดยน้ำหนักปัจจุบันเท่ากับน้ำหนักสุทธิรวมเดิม × (1 − เปอร์เซ็นต์ ÷ 100) ทุกครั้งใช้ฐานเดิม ไม่ลดทบจากการปรับก่อนหน้า
- ใช้สิทธิ์จัดการส่งออกยางของสาขาที่มีอยู่แล้ว รวม Admin ที่ได้รับสิทธิ์นี้ โดยไม่เพิ่มสิทธิ์ใหม่หรือขยายขอบเขตสาขา
- ปิดการปรับย้อนหลังเมื่อมีบิลรับเข้าที่อ้างอิงรายการ ผูกใบชั่งรถส่งออก WEX หรือมีสถานะขายแล้ว
- ปิดการปรับย้อนหลังเมื่อตัว REX ถูกล็อกในรายงาน ส่วนรายงานที่ล็อกเฉพาะรายการโอนค่าทำงานไม่เป็นเหตุห้ามปรับน้ำหนัก หากไม่เข้าเงื่อนไขห้ามอื่น
- คงน้ำหนักสุทธิรวมเดิม มูลค่ายาง อัตราและยอดค่าทำงาน ค่าดำเนินการอื่น รายการโอน สลิป และรายงานเดิมไว้ การปรับนี้เปลี่ยนเฉพาะน้ำหนักปัจจุบันและเปอร์เซ็นต์ลดลง โดยราคาปัจจุบันต่อกิโลกรัมคำนวณตามน้ำหนักใหม่
- เลือกกรอกได้ระหว่างเปอร์เซ็นต์ลดลงและน้ำหนักปัจจุบัน โดยมีตัวเลือกที่หัวข้อของแต่ละช่องให้เลือกได้ครั้งละหนึ่งอย่าง ช่องที่เลือกแก้ไขได้ อีกช่องเป็น readonly และแสดงผลคำนวณตาม ไม่คำนวณวนกลับไปแก้ค่าที่ผู้ใช้กำลังพิมพ์
- ใช้รูปแบบเลือกวิธีกรอกน้ำหนักเดียวกันทั้งรายการฉบับร่างที่เปิดตรวจสอบ และการปรับย้อนหลังของรายการที่ตรวจสอบแล้ว

ค่าทำงานรวมตามกติกาเดิมเท่ากับน้ำหนักสุทธิรวมเดิม × อัตราค่าทำงาน + ค่าดำเนินการอื่น และยอดโอนค่าทำงานตัดเศษลงเป็นบาท สูตรทั้งสองไม่ใช้น้ำหนักปัจจุบันหรือเปอร์เซ็นต์ลดลง จึงไม่ต้องแก้ยอดโอนเพื่อปรับน้ำหนัก แต่ห้ามสรุปว่าข้อมูลทุกหน้าไม่เปลี่ยน เพราะราคาเฉลี่ยและข้อมูลที่อิงน้ำหนักอาจเปลี่ยนตาม

## ขอบเขตการบันทึก

บันทึกการปรับรายการที่ตรวจสอบแล้วผ่าน `PATCH /api/lanflow/rubber-exports/[exportId]/weight` และ `adjust_rubber_export_weight` เท่านั้น โดยตรวจสิทธิ์เดิมซ้ำหลังรอล็อกสาขา ตรวจเงื่อนไขห้าม และเทียบน้ำหนักที่ผู้ใช้เปิดดูไว้กับค่าล่าสุดก่อนเขียน ป้องกันการแก้ทับค่าที่เปลี่ยนไปแล้ว การส่งค่าน้ำหนักเดิมซ้ำไม่เพิ่มประวัติ

ใช้ private transaction context เปิดข้อยกเว้นเฉพาะน้ำหนักปัจจุบันและเปอร์เซ็นต์ลดลงใน guard เดิม ไม่ใช้ค่า session ที่ผู้เรียกปลอมได้ ไม่เปิดแก้ข้อมูลการเงินหรือ snapshot อื่น รายงานที่ล็อกเฉพาะรายการโอนค่าทำงานจึงไม่ต้องถูกปลดล็อก

เก็บค่าเดิม/ใหม่ ผู้ปรับ เวลาปรับ และหมายเหตุไม่เกิน 300 ตัวอักษรใน `rubber_export_weight_adjustments` ภายใน transaction เดียวกัน ประวัติอ่านได้ตามสิทธิ์จัดการส่งออกยางเดิมและคงอยู่หลังลบต้นทาง รายละเอียดแสดงประวัติล่าสุดไม่เกิน 20 รายการ

## รูปแบบหน้าจอที่ยืนยัน

- ผู้ใช้เปลี่ยนตำแหน่งและรูปแบบเป็นปุ่มข้อความ “ปรับ” บริเวณช่องน้ำหนักปัจจุบัน `rubber-export-current-weight` แทนดินสอบนตัวเลขสรุป
- กด “ปรับ” แล้วเปลี่ยนพื้นที่ช่องน้ำหนักเดิมเป็นส่วนกรอกภายใน `landscape-modal-body modal-scroll-body` ของรายละเอียดเดิม ไม่เปิดหน้าต่างหรือ modal ใหม่ และยังเห็นข้อมูลส่วนอื่นของรายการ
- เรียงส่วนกรอกน้ำหนักปัจจุบันและเปอร์เซ็นต์ลดลงคู่กันบนจอกว้าง และเรียงลงบนมือถือ แต่ละส่วนมีตัวเลือก radio ที่หัวข้อในกลุ่มเดียวกันเพื่อเลือกได้เพียงหนึ่งวิธี อีกช่องอ่านอย่างเดียว มีพื้นหลังและข้อความ “คำนวณอัตโนมัติ · อ่านอย่างเดียว” ให้เห็นชัด
- เริ่มเลือกน้ำหนักปัจจุบันเมื่อเปิดฟอร์ม การสลับวิธีกรอกยังคงน้ำหนักที่คำนวณไว้เพื่อไม่ให้เกิดความคลาดเคลื่อนจากการปัดเปอร์เซ็นต์ จนกว่าผู้ใช้จะเปลี่ยนค่าช่องที่เลือก
- สำหรับฉบับร่างที่เปิดตรวจสอบ ใช้ตัวเลือกและสูตรเดียวกัน โดยการบันทึกและการตรวจสอบยังใช้ขั้นตอนฉบับร่างเดิม ไม่บันทึกเป็นการแก้ย้อนหลังของรายการที่ตรวจสอบแล้ว
- แสดงน้ำหนักก่อนและหลัง พร้อมยืนยันว่ายอดโอน สลิป และรายงานโอนคงเดิม ส่วนการ์ดสรุปน้ำหนัก เปอร์เซ็นต์ และราคาปัจจุบันต่อกิโลกรัมแสดงผลตามค่าที่กำลังกรอก
- ใช้ปุ่ม “ยกเลิก” และ “บันทึกน้ำหนัก” โดยปิดการบันทึกเมื่อค่าไม่ถูกต้องหรือไม่เปลี่ยนจากเดิม ข้อผิดพลาดแสดงติดกับช่องกรอก
- ผู้ไม่มีสิทธิ์ไม่เห็นปุ่มปรับ ผู้มีสิทธิ์แต่ติดเงื่อนไขห้ามให้เห็นเหตุผลในรายละเอียด ไม่อาศัย tooltip อย่างเดียว
- แสดงประวัติในรายละเอียดเดียวกัน และคืนโฟกัสที่ปุ่ม “ปรับ” หลังบันทึกหรือยกเลิก

ใช้ลดลง 0% สำหรับกรณีน้ำหนักเท่าเดิมแทน checkbox เดิม เพื่อให้มีชุดเลือกวิธีกรอกน้ำหนักเพียงชุดเดียว ฉบับร่างแสดงส่วนกรอกทันทีและใช้ปุ่มบันทึกร่าง/ตรวจสอบเดิม

- Regression ส่งออกยางเดิมผ่าน 6 กรณี อีกหนึ่งกรณี `explicit selection...` ติด fixture INSERT บิลยางด้วย service role เพราะ `permission denied for schema private` ก่อนเข้าขั้นตอนทดสอบ; baseline `HEAD:supabase-schema.sql` ให้ USAGE private เฉพาะ authenticated อยู่แล้ว งานนี้ไม่ได้เปลี่ยน grant ของ schema ดังกล่าว
- Lint, typecheck, source-size และ production build ผ่านในเครื่อง; ไม่ใช่หลักฐานว่า deploy หรือแก้ข้อมูล Cloud แล้ว

## Scrutiny และการแก้ fail paths — 2026-11-02

- เปอร์เซ็นต์อยู่ในช่วงที่ถูกต้อง แต่ปัดน้ำหนักแล้วเป็นศูนย์: ต้องตรวจผลน้ำหนักร่วมกับรูปแบบเปอร์เซ็นต์ เพื่อไม่ให้บันทึกฉบับร่างเป็น null โดยไม่มีข้อผิดพลาด; ทดสอบด้วยฐาน 0.01 กก. ลดลง 99.99%
- แยกการยืนยันบันทึกออกจากการอ่านข้อมูลหลังบันทึก: เมื่อ PATCH น้ำหนักสำเร็จ ให้คงน้ำหนักที่ยืนยันแล้วในรายละเอียด แม้การโหลดรายการ รายละเอียด หรือ cache จะล้มเหลว และแจ้งว่าบันทึกแล้วแต่โหลดข้อมูลไม่ครบ ไม่แจ้งว่าบันทึกล้มเหลวหรือปล่อยให้รายละเอียดกลับไปแสดงน้ำหนักเดิม
- ระหว่างบันทึกร่างหรือตรวจสอบ ต้องล็อกทั้งส่วนกรอกน้ำหนัก ค่าใช้จ่าย และปุ่มเขียนอีกฝั่ง เพื่อไม่ให้บันทึกร่างและตรวจสอบซ้อนกัน
- มี browser regression ที่ทำให้ทั้งสามปัญหาเกิดซ้ำก่อนแก้ พร้อมกรณีควบคุมและ isolated tests ของ mutation/read failure; ไม่พบ unused function/variable/import ในชุดไฟล์ที่ตรวจ
- หลังแก้ผ่าน UI 10 กรณี, isolated 29 กรณี, pgTAP 124 ข้อ, regression draft edit และ system-manager verification 2 กรณี รวมทั้ง build, lint, typecheck, source-size, service worker และ bundle-budget checks; ไม่ได้ขยายสิทธิ์ service role เพื่อข้ามข้อจำกัด fixture เดิม

## Scrutiny รอบสอง — canonical state และขอบเขตหน้ารายละเอียด

- หลังบันทึกต้องรับน้ำหนัก canonical จาก GET ล่าสุดเข้า local input ของ verified modal ด้วย แม้คง modal เดิมไว้เพื่อรักษา focus มิฉะนั้นการแก้ต่อจากผู้ใช้อื่นอาจแสดงค่าเก่าและเปิดบันทึกทับโดยไม่ตั้งใจ
- ค่าเปอร์เซ็นต์ที่อ่านอย่างเดียว derive จากน้ำหนักปัจจุบันโดยตรง เก็บ raw percent เฉพาะโหมดที่เลือกกรอกเปอร์เซ็นต์ และตัดฟังก์ชันส่งต่อ/การอัปเดตค่าซ้ำที่ไม่จำเป็น
- เก็บ AbortController ของหน้ารายละเอียดไว้ตลอดอายุการเปิด ไม่ล้างเมื่อ GET แรกจบ ปิดรายละเอียดเมื่อเปลี่ยนสาขา และปฏิเสธผล save/read/verify ที่กลับมาหลัง session เดิมถูกปิดหรือแทนที่
- การเลิกเปิดรายละเอียดไม่ยกเลิก mutation ที่ส่งแล้ว แต่หยุดอ่าน/แสดงผลในหน้าที่หมดอายุ หากขอบเขตรายการเปลี่ยนระหว่างรอ mutation ห้ามเริ่ม reload ของสาขาเดิม เพราะอาจ abort query ของสาขาใหม่; ให้ mark cache เดิม stale โดยไม่ refetch
- มี red-to-green browser repro ของ canonical weight และ keyboard branch switch พร้อม isolated cases ของ late write, late read, closed-before-write และ stale hook reload; ผ่าน UI 12 กรณี, isolated 34 กรณี และ existing draft/manager regressions 2 กรณี
- หลังแก้รอบสองผ่าน pgTAP 124 ข้อ, production build, lint, typecheck, source-size, service-worker และ bundle-budget checks เช่นเดิม โดยไม่แก้ Cloud หรือเพิ่มสิทธิ์ใหม่

## Scrutiny รอบสี่ — ปรับน้ำหนักพร้อมเปลี่ยนสถานะขาย
