# แผนส่งการแก้ไขและลบรับจ่ายเบื้องหลัง

วันที่: 2026-10-28 (Asia/Bangkok)
สถานะ: ดำเนินการและตรวจยืนยันครบ 4 Phase ใน Local แล้ว รายละเอียดสัญญา/rollout/rollback อยู่ใน `docs/income-expense-background-mutations.md` และ ADR 0085; checklist/หลักฐานอยู่ใน `10_Daily/2026-10-28 3.md` ของ vault codingDO ยังไม่ commit/push, apply Supabase Cloud หรือ deploy

## ขอบเขตที่ผู้ใช้ยืนยัน

- ปรับเฉพาะการแก้ไขและลบรายรับทั่วไป/ค่าใช้จ่ายให้ส่งเบื้องหลังเหมือนบิลยางล่าสุด
- คงพฤติกรรมการสร้างใหม่ บิลขาย และรายการโอนเงินตามเดิม
- เป้าหมายหลักคือทำงานเบื้องหลังให้มากที่สุด: ลดเวลารอหน้าฟอร์ม การกดส่งซ้ำ และข้อความรบกวน โดยไม่เปลี่ยนกติกาอนุมัติหรือถือว่ารับงานแล้วเท่ากับสำเร็จ

## กติกาคำขอรออนุมัติที่ผู้ใช้ยืนยัน

- ผู้ใช้เลือกใช้กติกาเก่า: ยังคงบล็อกการแก้ไข/ลบเมื่อรายการรออนุมัติ
- ไม่เพิ่มความสามารถส่งคำขอใหม่แทนคำขอรออนุมัติเดิม ข้อเสนอนี้ไม่ได้รับอนุมัติ
- การส่งคำขอเดิมซ้ำเพื่อยืนยันผลต้องไม่ทำรายการเงินซ้ำ; การป้องกันคำขอจากหลายแท็บ/เครื่องเป็นหน้าที่ของระบบ
- ไม่ถือว่าการส่งซ้ำเพื่อยืนยันผลเป็นการขอแทนที่หรือเจตนาใหม่ และไม่ได้อนุมัติให้แทนงานที่ยังไม่ทราบผลการส่งทุกกรณี

## การปิดงานค้างของรายการที่ถูกลบแล้วที่ผู้ใช้ยืนยัน

- ล้างงานแก้ไข/ลบค้างพร้อมร่างของงานนั้นโดยไม่แจ้งเตือน เมื่อระบบกลางที่ตรวจสิทธิ์แล้วระบุชัดว่ารายการต้นทางเดียวกันถูกลบจริง
- การค้นหาไม่พบ ข้อผิดพลาดเครือข่าย หรือไม่มีสิทธิ์ตรวจ ไม่ใช่หลักฐานว่าถูกลบ ต้องเก็บงานไว้
- ไม่รวมงานสร้างใหม่หรือร่าง/คำสั่งอื่น และไม่สร้างรายการที่ถูกลบกลับขึ้นมา

## การไม่เก็บร่างเมื่อข้อมูลถูกแก้ไขที่ผู้ใช้ยืนยัน

- หากรายการยังอยู่ แต่ระบบยืนยันว่าข้อมูลถูกแก้ไขไปก่อนจนคำขอแก้ไข/ลบค้างขัดแย้งกับข้อมูลล่าสุด ให้ทิ้งร่างและปิดงานค้างของคำขอนั้น
- ไม่ส่งทับข้อมูลล่าสุด ไม่ปรับคำขอเก่าไปใช้ข้อมูลล่าสุดแล้วส่งเอง และไม่แตะร่างหรืองานใหม่ของคำขออื่น
- กติกานี้ต่างจากบิลยางที่เก็บร่างเมื่อรายการยังอยู่แต่ revision เปลี่ยน
- ไม่ครอบคลุมผลที่ยังไม่แน่ชัด ข้อผิดพลาดเครือข่าย หรือการไม่มีสิทธิ์ตรวจ ซึ่งยังต้องเก็บงานไว้
- เมื่อทิ้งร่างเพราะข้อมูลเปลี่ยน ให้เก็บเหตุให้ผู้ใช้ทราบครั้งเดียวว่ารายการเปลี่ยนแล้ว ยกเลิกการแก้ไข/ลบที่ค้างไว้ และให้ตรวจข้อมูลล่าสุด ไม่แจ้งซ้ำจากการตรวจหรือส่งงานเดิมซ้ำ; หากเป็นสาขาอื่นให้รอแสดงเมื่อกลับมาดูรับจ่ายของสาขานั้น ไม่เด้งข้ามสาขา

## เงื่อนไขออนไลน์และการรับงานที่ผู้ใช้ยืนยัน

- การแก้ไข/ลบรายการที่บันทึกในระบบกลางแล้วต้องออนไลน์เพื่อตรวจสถานะล่าสุดก่อนรับงานไว้ในเครื่อง
- เมื่อเก็บงานในเครื่องสำเร็จแล้วจึงปิดฟอร์มและส่งต่อเบื้องหลัง การรับงานยังไม่ใช่การยืนยันผลธุรกิจสำเร็จ
- หากรับงานแล้วเน็ตหลุด งานยังอยู่และส่งต่อเมื่อเชื่อมต่อได้ โดยไม่ต้องเปิดฟอร์มรอ
- เมื่อเปลี่ยนหน้าเมนู งานที่รับไว้แล้วยังคงส่งเบื้องหลังต่อ
- เมื่อปิดแอป งานที่ยังไม่เสร็จเก็บไว้และส่งต่อเมื่อเปิดแอปกลับมา ภายใต้บัญชีและสิทธิ์ที่ถูกต้อง ไม่รับประกันส่งต่อขณะปิดเบราว์เซอร์
- แสดงปัญหาที่ต้องให้ผู้ใช้จัดการในบริบทสาขาของงาน โดยคงข้อยกเว้นการปิดเงียบเมื่อยืนยันว่ารายการถูกลบแล้ว; งานสาขาอื่นไม่เด้งแจ้งแทรก

## การส่งต่อเมื่อเปลี่ยนสาขาที่ผู้ใช้ยืนยัน

- งานแก้ไข/ลบรายรับทั่วไปและค่าใช้จ่ายที่รับไว้แล้วต้องส่งต่อจนเสร็จ แม้ผู้ใช้เปลี่ยนไปสาขาอื่น ไม่พักงานเพียงเพราะไม่ได้เลือกสาขาเดิม
- ผลยังผูกกับรายการและสาขาต้นทาง ไม่เปลี่ยนเป็นรายการของสาขาที่เปิดอยู่
- ผู้ใช้ต้องการกติกาส่งต่อเมื่อเปลี่ยนสาขาสำหรับบิลยางด้วย โดยให้สร้างแชตใหม่เฉพาะบิลยางเพื่อถามรายละเอียดต่อ ส่วนรับจ่ายยังอยู่ในแชตนี้

## การเปลี่ยนบัญชีเมื่อมีงานค้างที่ผู้ใช้ยืนยันล่าสุด

- เมื่อออกจากระบบหรือเปลี่ยนบัญชี ให้พักงานรับจ่ายของบัญชีเดิมไว้จนบัญชีนั้นกลับเข้าสู่ระบบและมีสิทธิ์อีกครั้ง
- ห้ามส่งงานของบัญชีเดิมโดยใช้บัญชีใหม่ งานยังผูกกับบัญชีและสาขาต้นทาง
- การเปลี่ยนสาขาภายในบัญชีเดิมยังส่งงานต่อจนเสร็จตามข้อตกลงข้างต้น
- ข้อนี้ใช้คำยืนยันล่าสุดในแชตรับจ่าย แทนข้อความเดิมในเอกสารที่ระบุว่าห้ามเปลี่ยนบัญชีเมื่อมีงานค้าง

### ข้อยืนยันเพิ่มเติม — 2026-10-29

- หากระบบยืนยันว่าการเข้าสู่ระบบปัจจุบันถูกเพิกถอน ให้กลับหน้าเข้าสู่ระบบทันทีตามพฤติกรรมเดิม โดยเก็บคิวรับจ่ายไว้ในเบราว์เซอร์/โปรไฟล์เดิมและผูกบัญชีเจ้าของงาน เครือข่ายล้มเหลวเพียงอย่างเดียวไม่ใช่หลักฐานการเพิกถอน
- คำขอที่ยังส่งไม่ถึงส่วนกลางเห็นคิวเฉพาะเบราว์เซอร์เดิม อีกเครื่องไม่รับช่วงส่งคิวนี้ ส่วนผลที่ส่วนกลางบันทึกหรือคำขอรออนุมัติแล้วเห็นจากเครื่องอื่นตามสิทธิ์ แม้เครื่องต้นทางยังยืนยันผลไม่ได้
- ข้อยืนยันนี้คงพฤติกรรมเดิม ไม่เปลี่ยนคิวรับจ่ายเป็นคิวกลางแบบบิลยาง และผู้ใช้ยืนยันเก็บการแก้ quiet session precheck ของรอบนี้ไว้

## การทำงานเงียบของสาขาอื่นที่ผู้ใช้ยืนยันล่าสุด

- งานของสาขาอื่นยังส่งและตรวจผลเบื้องหลังต่อ โดยไม่เด้งข้อความ หน้าต่าง หรือการแจ้งเตือนแทรกระหว่างทำงานในสาขาปัจจุบัน
- ไม่ย้ายหน้า เปิดฟอร์ม เปลี่ยนสาขา หรือบล็อกฟอร์ม/เมนูที่กำลังใช้งานเพราะผลของงานสาขาอื่น
- ข้อยกเว้นที่ยืนยันแล้วคือการกลับหน้าเข้าสู่ระบบเมื่อระบบยืนยันว่าการเข้าสู่ระบบปัจจุบันถูกเพิกถอน ซึ่งมีผลต่อบัญชีทุกสาขา
- เก็บสถานะและเหตุที่ต้องจัดการตามบัญชี/สาขาต้นทาง แล้วแสดงในหน้ารับจ่ายเมื่อผู้ใช้กลับมาดูสาขานั้น ไม่เปิดข้อความย้อนหลังเรียงกันหลายรายการ
- การไม่เด้งแจ้งเตือนข้ามสาขาไม่ใช่การลบหรือทำเครื่องหมายว่ารับทราบปัญหาแล้ว ต้องไม่ทำให้เหตุที่ควรแสดงภายหลังสูญหาย แม้คำขอส่งถูกปิดไปแล้วตามกติกา
- ตรวจบัญชีและสิทธิ์อีกครั้งก่อนแสดง เก็บเหตุครั้งเดียวตามคำขอและเหตุ ไม่แสดงข้อมูลให้บัญชีอื่นหรือสาขานอกสิทธิ์
- ข้อนี้แทนกติกาเดิมที่อนุญาตแจ้งครั้งเดียวพร้อมชื่อสาขา/เลขรายการขณะเปิดสาขาอื่น; ปรับเฉพาะแผนรับจ่ายนี้ ไม่เปลี่ยนงานบิลยางของแชตแยกอัตโนมัติ

## รายละเอียดภาพรวมที่ผู้ใช้ยืนยันแล้ว

ผู้ใช้ยืนยันรายละเอียดภาพรวมและให้จัดทำแผนลง Obsidian โดยรอคำสั่งเริ่มจากผู้ใช้:

- รายการล่าสุดแสดงข้อมูลที่ระบบกลางยืนยัน พร้อมสถานะกำลังส่งแก้ไข/ลบ; คำขอลบยังไม่ทำให้แถวหายก่อนทราบผล และไม่ใช้ยอดร่างเปลี่ยนยอดเงินจริง
- ป้องกันแก้ไข/ลบซ้ำระหว่างคำขอเดียวกันยังยืนยันผลไม่ได้ โดยไม่บล็อกการใช้เมนูหรือรายการอื่น
- ส่งและตรวจผลอัตโนมัติเมื่อเชื่อมต่อได้ ตรวจซ้ำเป็นช่วงที่เหมาะสมเมื่อยังมีงาน ไม่เรียกซ้ำถี่หรือทำงานธุรกิจซ้ำ
- งานที่สำเร็จตามปกติอัปเดตสถานะและข้อมูลโดยไม่เปิดหน้าต่างบังคับรอหรือแจ้งสำเร็จซ้ำทุกครั้ง
- ปัญหาชั่วคราวจากเครือข่ายให้ลองใหม่เบื้องหลัง ไม่แจ้งซ้ำทุกครั้งที่ลอง; ปัญหาที่ต้องให้ผู้ใช้จัดการให้แสดงเหตุครั้งเดียวในบริบทสาขาของงาน
- ผลของงานสาขาอื่นเก็บสถานะไว้เงียบ ๆ แสดงเมื่อกลับมาดูรับจ่ายของสาขานั้นพร้อมเลขรายการ เฉพาะบัญชีเดิมที่ยังมีสิทธิ์ ไม่เด้งข้ามสาขา ไม่ย้ายหน้า เปิดฟอร์ม หรือบล็อกงานปัจจุบัน
- สิทธิ์ ล็อก และการปฏิเสธธุรกิจยังใช้กติกาเดิม ห้ามวนส่งคำขอที่ทราบแล้วว่าไม่ผ่านอย่างต่อเนื่อง และไม่ทิ้งงานกรณีไม่มีหลักฐานให้ปิดตามกติกาที่ตกลง

## ปรับแผนหลัง Scrutinize — 2026-10-28

ผู้ใช้สั่งปรับแผนตามผล review ทั้ง 6 จุดต่อไปนี้ เป็นข้อกำหนดสำหรับงานในอนาคต ไม่ใช่รายงานว่าพบและแก้บั๊กจากการทดลองแล้ว

1. **Replay ไม่ฟื้นคำขอที่จบแล้ว:** แยกการยืนยันคำขอเดิมออกจากผู้ใช้เริ่มคำขอใหม่ ตรวจ approved/rejected และสถานะสิ้นสุดที่ระบบรองรับก่อนสร้าง approval ห้าม retry อัตโนมัติเปลี่ยนเป็นคำขอใหม่เมื่อถูกปฏิเสธ ไม่เปิดความสามารถแทนคำขอรออนุมัติ ต้องระบุหลักฐานคำขอเดิมที่ยังตรวจได้หลังมีการแก้ไขครั้งต่อมาหรือเก็บกวาดประวัติ; หากยังยืนยันไม่ได้ให้คงงาน ไม่สรุปว่ายังไม่เคยสำเร็จหรือทิ้งร่างด้วยเหตุผิด
2. **หยุดตามบัญชีจริงทุกจุดส่ง:** งานเบื้องหลัง/ลองส่งรายรายการต้องใช้เงื่อนไขเจ้าของคิวเดียวกัน ตรวจการเปลี่ยน session ระหว่างรายการและจากอีกแท็บก่อนเริ่มคำขอถัดไป พร้อมขอบเขตการตรวจผู้ส่งฝั่ง Server ที่ปิดช่องเปลี่ยนบัญชีระหว่างตรวจและส่งได้ ไม่ใช้ผู้สร้างเอกสารเดิมแทนผู้ส่งคำขอ และไม่อ้างว่า abort ย้อนธุรกิจที่ commit แล้ว
3. **คัดเฉพาะงานใหม่ในขอบเขต:** กำหนด marker/contract สำหรับ general update/delete รุ่นใหม่เท่านั้นก่อนขยายส่งข้ามสาขา งาน create/sale/transfer และคิวเก่าไม่มี marker คง behavior เดิม ไม่ตีความเป็น background ใหม่อัตโนมัติ ใช้การตรวจผลและปิด exact command ชุดเดียวกันทั้ง auto/manual; เส้นทาง stock retry เป็น regression boundary ไม่ขยายขอบเขตไปบิลขาย
4. **ปิดคิวพร้อมเก็บเหตุอย่าง atomic:** การทิ้ง conflict ต้องบันทึกเหตุรอแสดงร่วมกับการปิด exact queue ใน transaction เดียวกันหรือกลไกกู้คืนที่พิสูจน์ได้ ระบุ store, identity, อายุเก็บ และการทำเครื่องหมายแสดงแล้ว ไม่อาศัย marker บนคิวที่ถูกลบ; ใช้ primitive เดิมที่เหมาะสมก่อนเพิ่ม abstraction และตัดสิน schema/IDB upgrade จาก stores จริงพร้อม compatibility/blocked-tab handling หากจำเป็น
5. **จำกัดภาระหลายสาขา:** อ่านคิวของบัญชีเป็นรอบแล้วจัดกลุ่มเฉพาะสาขาที่มีงาน eligible จำกัด concurrency และ retry ด้วย backoff ที่เหมาะสม ไม่สร้าง timer ต่อสาขาหรือไล่ส่งทุกสาขาที่มีสิทธิ์ ปัญหาสาขาหนึ่งไม่กักงานสาขาอื่น; invalidate เฉพาะเมื่อผลเปลี่ยนจริงและรวม shared refresh ต่อรอบ ตรวจผลแถบ service-health ด้วย ไม่ใช่แค่ปิด toast โดยไม่ซ่อนเหตุระบบล่มจริงหรือข้าม session/lock
6. **เพิ่มกรณีฟอร์มผสมและปรับ tests แบบแยกรุ่น:** ฟอร์มแก้ไขสามารถมีบรรทัดเพิ่มใหม่ ต้องแยกผลต่อบรรทัดและรักษาบรรทัดที่ล้มเหลว หาก update รับไว้แล้วแต่ create ไม่ผ่าน การกดบันทึกซ้ำต้องไม่ส่ง update ซ้ำ/ชนกับงานที่รับแล้ว ปรับ test เดิมให้ยังตรวจคิวเก่า/create/sale ตามเดิม และเพิ่ม test ใหม่เฉพาะงานมี marker ไม่แก้ expectation ทั้งชุดให้ผ่านอย่างเดียว

## แนวทางทำงาน 4 ระยะหลังได้รับคำสั่งเริ่ม

1. **สัญญาและขอบเขต:** Trace UI/queue/approval/RPC/feed ให้ครบ ตัดสิน replay/terminal proof, marker/legacy, account binding, atomic outcome และ schema compatibility ให้ชัดก่อนเริ่มเปลี่ยนตัวส่ง; ใช้คิวและ primitive เดิม ไม่สร้าง universal sync framework เส้นทางรายละเอียดบิลขายที่ตอบ 404 ใช้เป็นหลักฐานการลบไม่ได้
2. **รับงานและส่งอย่างทนทาน:** รับ general update/delete เมื่อ context/การเก็บในเครื่องสำเร็จ ส่งเฉพาะงาน eligible ทุกสาขาของเจ้าของบัญชี จัดการ retry/ผลเก่า/session/cleanup และฟอร์มผสม พร้อม behavioral tests ของแต่ละส่วน
3. **แสดงผลและความเงียบ:** แสดง authoritative rows/pending ไม่ปนยอดร่าง เก็บเหตุอย่างกู้คืนได้ ไม่แจ้งแทรกข้ามสาขา จำกัด scheduling/refresh และตรวจ browser ที่หน่วง POST จริง รวมบัญชีหลายสาขา
4. **ตรวจรวมและส่งมอบ:** ตรวจ acceptance/regression ตามแผน Daily แล้วรัน verify รวมครั้งสุดท้ายหลัง focused tests ผ่าน รัน API/DB/concurrency ตามส่วนที่เปลี่ยน ตรวจ compatibility/rollback และอัปเดต checklist จากหลักฐานจริง ไม่รัน full suite ซ้ำทุกขั้นโดยไม่มีเหตุ

กรณีตรวจรับที่เพิ่ม: response หายแล้วถูกปฏิเสธก่อน replay; งานเคยสำเร็จแล้วมี revision ถัดไป; เปลี่ยนบัญชีกลาง batch/จากอีกแท็บ; คิวผสมใหม่/เก่า/create/sale; crash ระหว่างปิดคิวกับเก็บเหตุ; หลายสาขาและ shared refresh/service banner; ฟอร์ม update+create ที่สำเร็จเพียงบางบรรทัด; manual/auto retry แข่งกัน

เอกสารนี้ยังไม่อนุญาตให้ deploy หรือทดสอบแก้ข้อมูล Production การเปลี่ยนบิลยางอยู่ในแชตเฉพาะบิลยาง
