# แผนบิลยาง: รับงานในเครื่องและประมวลผลผ่านคิวกลาง

วันที่: 2026-10-28  
สถานะ: ผู้ใช้สั่งเริ่มแล้ว — implementation และ verification อยู่ใน `docs/rubber-central-queue-verification.md`; checklist งานจริงอยู่ใน Daily ที่ระบุด้านล่าง  
ขอบเขต: บิลยางเท่านั้น  
ฉบับ: 2 — รวมกติกาปัจจุบันและลดเส้นทางประมวลผลซ้ำ

## เป้าหมายและแหล่งติดตามงาน

ให้สร้าง/แก้ไข/ลบบิลยางรับงานถาวรแล้วทำต่อเบื้องหลัง โดยระบบกลางเป็นผู้ประมวลผลหลัก ทุกเครื่องที่มีสิทธิ์เห็นสถานะร่วมกัน และรายงานล่าสุดไม่ข้ามงานค้างของสาขานั้น

เส้นทางหลักมีเพียง **เก็บงานในเครื่อง → ส่งเข้าคิวกลาง → ระบบกลางประมวลผล → ทุกเครื่องอ่านผล** เครื่องผู้ใช้ไม่เป็น worker แข่งกับระบบกลาง การลองใหม่จากเครื่องหมายถึงอัปโหลดคำสั่งเดิม/ขอให้ระบบกลางลองใหม่/อ่านผลตามสถานะ ไม่ส่งแก้ข้อมูลธุรกิจผ่านเส้นทางใหม่ที่หลบคิว

Daily `codingDO/10_Daily/2026-10-28 4.md` เป็นแหล่งสถานะ checkbox และหลักฐานหลังเริ่มงาน เอกสารนี้เป็นข้อตกลงผลิตภัณฑ์และขอบเขตทางเทคนิค ไม่เป็นหลักฐานว่า implementation หรือ Production เปลี่ยนแล้ว

ผู้ใช้สั่งให้รอเริ่มจากตน การปรับแผนครั้งนี้ไม่อนุญาตให้เริ่มแก้ source, รันการทดสอบพฤติกรรมใหม่, สร้าง/apply migration, commit/push หรือ deploy ไม่มีการตั้ง automation ของ Codex ให้ทำต่อ

## เป้าหมายล่าสุด — ลดการกลับมาจัดการบิลย้อนหลัง

ผู้ใช้ยืนยันแนวทางให้รับบิลแล้วปิดงานอัตโนมัติให้ได้มากที่สุด เหลือเฉพาะเรื่องที่ระบบตัดสินใจแทนไม่ได้เป็นงานของคน โดยยืนยันว่าให้จัดลำดับสร้าง/แก้ไข/ลบบิลให้ครบเส้นทางก่อน แล้วค่อยขยาย action อื่นที่รองรับเข้าคิวกลาง ไม่ยกเลิกเป้าหมายทุกเครื่องเห็น/จัดการตามสิทธิ์

- ตรวจข้อมูล ราคา/กติกาที่พร้อมใช้งาน สิทธิ์และข้อขัดข้องที่ตรวจได้ก่อนรับงานให้ผู้ใช้แก้ ณ จุดนั้น ไม่ตั้งใจรับคำสั่งที่รู้แน่ว่าผิดไปเป็นงานแก้ย้อนหลัง ขณะ offline ตรวจได้เฉพาะหลักฐานที่มีในเครื่อง ยังคงตรวจ Server จริงก่อนทำธุรกิจ
- งานปกติที่กลางรับแล้วเริ่มทำโดยเร็ว เป้าคือเข้ารายการปกติอัตโนมัติหรือรออนุมัติตามกฎ คิวเป็นสถานะติดตามงานระหว่างยังไม่จบ ไม่เพิ่มการกดส่ง/กดซิงก์รายบิลสำหรับเหตุชั่วคราว
- transient/cash-count/permission pause ให้ระบบดูแล retry/resume ตาม contract เดิม; confirmed stale/rejected ตามข้อตกลงปิดงานเก่าและเก็บเหตุ โดยไม่กลับมาเป็นงานให้แก้เองทุกครั้ง
- รวมเฉพาะ actionable exceptions ที่ต้องให้คนตัดสินใจไว้จุดดูงานเดียวเชื่อมรายการรออนุมัติ/ร่างออฟไลน์ที่ต้องแก้เดิม แต่ละแถวบอกเหตุและทางไปทำต่อ ไม่สร้างสำเนา approval queue หรือ business data อีกชุด ไม่แก้ราคา น้ำหนัก ยอดเงินหรืออนุมัติแทนผู้ใช้
- ก่อนผู้ใช้สร้างรายงาน ให้ precheck/ปลุกประมวลผลงานที่พร้อมอีกครั้งแบบ bounded ตามที่ออกแบบ ว่างแล้วผู้ใช้ดำเนินการเดิมได้ หากยังติดให้แสดงเฉพาะ blocker ที่ต้องจัดการ ห้ามสร้างรายงานอัตโนมัติหรือถือ branch/report lock ค้างรอ worker เพราะ worker ใช้ lock เดียวกัน การสร้างจริงยังต้องตรวจซ้ำใน transaction
- กำหนดผลวัดใน P1.6/P5.2 ได้แก่สัดส่วนงานจบเอง จำนวนงานที่ต้องกลับมาแก้ อายุคิว และสาเหตุที่ต้องให้คนทำ ไม่ตั้งตัวเลขรับประกันโดยยังไม่มี baseline
- ผู้ใช้ยืนยันให้ใช้วัน/เวลาที่ระบบกลางรับงานสำเร็จตรวจเงื่อนไขวันที่และช่วงเวลาแก้ไข เพื่อไม่ให้คิวล่าช้าทำให้ต้องอนุมัติเพิ่ม สิทธิ์ ล็อก และข้อมูลล่าสุดยังตรวจตอนทำงานจริง ผู้ใช้ยืนยันให้ใช้กติการาคาที่ระบบกลางตรวจผ่านตอนรับงานด้วย ราคาที่กรอกไม่เปลี่ยน และไม่เพิ่ม price approval เพียงเพราะเพดานลดระหว่างรอคิว

## กติกาผลิตภัณฑ์ปัจจุบัน

### รับงานและขอบเขตคิว

- สร้าง แก้ไข และลบ: ปิดฟอร์มหลังผ่านการตรวจที่จำเป็นและเก็บงานถาวรในเครื่องสำเร็จเท่านั้น ไม่รอ POST หรือ invalidation; context/storage failure ต้องกลับให้แก้ในฟอร์ม
- แยก “รับไว้ในเครื่อง”, “ระบบกลางรับเข้าคิว”, “กำลังประมวลผล”, “รออนุมัติ” และ “บันทึกสำเร็จ” ห้ามใช้การรับคิวแทนผลสำเร็จธุรกิจ
- เปลี่ยนหน้า/สาขาภายในบัญชีเดิมไม่พักงานที่รับไว้ รวมงานยังไม่เริ่มส่ง A ติดปัญหาไม่ขวางงาน B
- งานที่ยังไม่อัปโหลดมีเฉพาะต้นทาง ต้องรอออนไลน์ก่อนจึงเห็นร่วมกัน คิวกลางไม่สามารถเห็นงานที่ไม่เคยถูกส่งถึงระบบ
- งานทุกชนิดในขอบเขตบิลยางที่รองรับการทำต่อให้เข้าคิวกลาง ต้องทำบัญชี action ก่อนพัฒนา ไม่ตีความว่าให้สร้างฟีเจอร์ใหม่หรือขยายไปโมดูลอื่น การถ่ายรูป กรอก/ตรวจฟอร์ม การตัดสินใจอนุมัติ และการเปิดพิมพ์ยังเป็นการกระทำของผู้ใช้/เครื่อง
- ผู้ใช้ยืนยันให้งาน “อนุมัติ” และ “ลบคำขอรออนุมัติ” เข้าคิวกลาง หลังผู้จัดการผู้มีสิทธิ์กดยืนยันและตรวจ/เก็บคำสั่งถาวรสำเร็จ ให้ปิดหน้าต่างไปทำงานอื่นได้ ไม่รอผลธุรกิจและไม่ต้องกลับมากดซ้ำ คงข้อกำหนดเริ่มงานออนไลน์เดิม ไม่เพิ่มการอนุมัติออฟไลน์จากการตกลงครั้งนี้
- การรับคำสั่งอนุมัติ/ลบคำขอไม่ใช่ผลสำเร็จ แสดง “กำลังดำเนินการ” จนกลางยืนยัน; เมื่ออนุมัติสร้าง/แก้ไขสำเร็จบิลเข้ารายการปกติ อนุมัติลบให้บิลออก เมื่อคำสั่งลบคำขอสำเร็จให้นำ pending request นั้นออกตามกติกาเดิม ไม่ลบบิลจริงจากการลบคำขอ
- ผูก manager command กับผู้ยืนยัน สาขา และ request ID/รุ่นข้อมูลที่ผู้จัดการเห็น ไม่อนุมัติคำขอทดแทนหรือ revision ใหม่โดยอัตโนมัติ ตรวจสิทธิ์/ล็อก/ข้อมูลล่าสุดตอนทำงาน ถ้าคำขอถูกแทนหรือจบแล้วให้คืนผลตรงคำสั่งอย่างปลอดภัย ไม่ฟื้นคำขอ/ผลธุรกิจและไม่ขอให้กดซ้ำเพียงเพราะคำตอบหาย
- ใน flow ที่อ่านยังไม่พบ action ปฏิเสธแยก คำอธิบายก่อนหน้าที่เอ่ย “ปฏิเสธ” ไม่ใช่ข้อยืนยันให้เพิ่ม action ใหม่ ส่วน settings/OCR/action อื่นยังต้องระบุใน action matrix ไม่อาศัยคำว่า “ทุกงาน” ขยายสิทธิ์
- คงข้อจำกัดออฟไลน์เดิม: สร้างที่เข้าเงื่อนไขได้ แต่แก้/ลบบิลที่ซิงก์แล้วและหักสินค้าตัดสต็อกต้องออนไลน์ OCR ที่ยังเป็นรูป/ร่างไม่ได้ตรวจบันทึกไม่ใช่งานบิลที่รับแล้ว

### ผู้ประมวลผล บัญชี และสิทธิ์

- เมื่อระบบกลางรับแล้วต้องประมวลผลต่อได้แม้ทุกเครื่องปิด โดยมี retry/recovery ฝั่งกลาง เครื่องอื่นที่มีสิทธิ์เห็นและจัดการข้อยกเว้นได้ ไม่มีการสวมบัญชีต้นทาง
- คิวที่ยังอยู่เฉพาะในเครื่อง: logout/เปลี่ยนบัญชีให้พักจนบัญชีเจ้าของกลับมาและมีสิทธิ์ ห้ามอัปโหลดผ่านบัญชีอื่น
- การ logout อย่างเดียวไม่ถอนคำสั่งที่รับในระบบกลางแล้ว และไม่บังคับให้กลางรอบัญชีต้นทางออนไลน์ แต่สิทธิ์ธุรกิจยังต้องตรวจตาม contract
- ถูกถอนสิทธิ์สาขาหรือบัญชี inactive: พักงานที่ขาดสิทธิ์ ไม่ทิ้ง คืนสิทธิ์แล้วทำต่อเอง ไม่ย้าย actor ไปบัญชีอื่นอัตโนมัติ การให้ผู้มีสิทธิ์อื่นรับผิดชอบ/แก้/เริ่มใหม่ต้องผ่าน action contract และบันทึกผู้กระทำแยกจากผู้สร้างเดิม
- ผู้ใช้ยืนยันว่าเมื่อบัญชีเจ้าของงานถูกปิดถาวรจนงานค้างขวางรายงาน ผู้จัดการที่มีสิทธิ์สาขานั้นเลือกทิ้งงานค้างในคิวกลางได้ ต้องกดยืนยัน บันทึกบัญชีผู้ดำเนินการ/เวลา/คำสั่งเป้าหมาย และทิ้งเฉพาะคำสั่งค้าง ไม่ลบบิลจริงหรือคำขออื่น ไม่ทำอัตโนมัติเพียงเพราะบัญชี inactive/สิทธิ์หายชั่วคราว ต้องตรวจหลักฐานสถานะบัญชีตาม contract
- การทิ้งโดยผู้จัดการต้องทำบนสถานะ/รุ่นคำสั่งล่าสุดและ serialize กับ worker ก่อนปิด หากธุรกิจสำเร็จไปแล้วให้ reconcile ผลจริง ไม่ย้อนข้อมูลหรือแจ้งว่าทิ้งการเปลี่ยนแปลงสำเร็จ งานที่ยังไม่ทราบผลต้องตรวจยืนยันก่อน บันทึก terminal receipt ป้องกันอีกเครื่องฟื้น และปลด report blocker เฉพาะงานที่ปิดแล้ว หากยังมี pending approval/บิลราคาไม่ครบ/งานอื่นให้คงตัวขวางเดิม
- ข้อยกเว้นนี้เป็นการกดยืนยันโดยผู้จัดการ ไม่เปลี่ยนข้อกำหนดให้เก็บต้นฉบับสร้างออฟไลน์อัตโนมัติ การยืนยันต้องแสดงผลของการทิ้งร่างที่ยังไม่ถูกบันทึกอย่างชัดเจน และไม่อ้างว่ากลางล้างสำเนา offline-only ของเครื่องที่ยังไม่เคยอัปโหลดได้
- แยก creator, ผู้สั่งคำสั่ง, ผู้อนุมัติ, ผู้จัดการข้อยกเว้น และระบบที่ประมวลผล ห้ามแก้ผู้สร้างย้อนหลังหรือเก็บ session/token ผู้ใช้เพื่อให้ worker ทำงาน
- ผลสำเร็จตรงคำสั่งที่กลับมาหลัง logout/เปลี่ยนบัญชีเก็บให้บัญชีเดิมเงียบ ๆ ไม่แจ้งหรือพิมพ์ในบัญชีใหม่ และไม่ส่งงานสำเร็จซ้ำ
- สิทธิ์เห็นคิวไม่ใช่สิทธิ์แก้/ทิ้ง/อนุมัติ ต้องบังคับ API/DB/RLS และรักษา OCR ownership เดิม ไม่ใช้สิทธิ์ service เป็นเหตุข้ามกฎ

### ผลลัพธ์และการทิ้งงาน

| เหตุ/ผลที่ตรวจสอบตรงคำสั่ง | การจัดการ |
| --- | --- |
| synced | ปิดงานค้าง โหลดบิลจริงเข้ารายการปกติ; ลบสำเร็จให้บิลออกจากรายการ |
| pending_approval | ขั้นตอนส่งจบ แสดงรออนุมัติเดิม ไม่ส่งซ้ำ ไม่ถือว่าบิลมีผลแล้ว |
| ข้อมูลบิลเปลี่ยนหรือมีคำขอใหม่กว่าจนงานเก่าส่งไม่ได้ | ทิ้งเฉพาะงาน/ร่างเก่า คงบิลและคำขอใหม่ แจ้งตาม scope |
| แก้/ลบถูกปฏิเสธยืนยันจากข้อมูลไม่ถูกต้องหรือ report/transfer lock | ทิ้งเฉพาะงาน/ร่างที่ถูกปฏิเสธ บิลส่วนกลางคงอยู่ แจ้งตาม scope |
| สร้างออฟไลน์ที่ยังไม่มีบิลบนกลาง แล้วข้อมูลไม่ผ่าน | เก็บต้นฉบับเพื่อแก้และส่งใหม่ ไม่ลบทิ้งอัตโนมัติ |
| transient/network/timeout/ผลผิดรูปแบบ/identity ไม่ตรง | เก็บคำสั่งเดิม รอผล/ลองใหม่ ไม่สรุปว่า Server ไม่ได้ commit |
| ล็อกนับเงินชั่วคราวหรือขาดสิทธิ์ | พักตามเหตุ เริ่มต่อเมื่อพร้อม ไม่ขวางสาขาอื่น |
| authorized proof ว่าบิลเดียวกันถูกลบแล้ว สำหรับแก้/ลบ | ปิดงานตรงตัวเงียบ ๆ ตาม ADR-0084 ไม่ถือว่าไม่พบ=ลบ |

การทิ้งเป็นผลถาวรของคำสั่งเดิม ต้องมี minimal terminal receipt กลางให้เครื่องเก่าตรวจได้ก่อน cleanup payload ไม่ใช่แค่ลบ IndexedDB หรือซ่อนแถว หน้าต่าง/อุปกรณ์ที่กลับมาภายหลังต้องไม่ฟื้นงานที่สำเร็จ/ทิ้ง/ยกเลิกแล้ว

งานใหม่ที่ผู้มีสิทธิ์ตั้งใจแทน pending approval ยังคงใช้กฎ replacement เดิม ห้ามหมุน UUID/rebase คำสั่งเก่าเอง การแก้คำสั่งที่ถูกปฏิเสธต้องเป็น intent ใหม่ตาม contract พร้อมตรวจ current context ไม่เปลี่ยน immutable payload ของคำสั่งที่กลางรับแล้ว

### รายงานและนับเงิน

- ใช้กฎรายงานทั่วไปเดิมของบิลยาง: ขวางเฉพาะสาขาที่มีงานตามจุดตรวจ/cutoff เดิม คงบิล active ราคาไม่ครบ/ศูนย์และ pending approval blockers เพิ่มคิวกลางที่ยังไม่จบใน scope เดียวกัน ไม่ขวางทุกสาขา
- queued/running/retry/paused/correction-required ที่ยังไม่จบต้องมี mapping ตัวขวางชัดเจน งาน terminal และประวัติ/ข้อความเหตุไม่ขวางต่อเพียงเพราะแถวยังเก็บอยู่
- เปลี่ยน queue blocker เป็น pending-approval blocker พร้อมผลคำสั่งในธุรกรรมเดียว ไม่มีช่องว่างสร้างรายงานแทรกและไม่นับซ้ำ
- รับคิว สร้างผลธุรกิจ เปลี่ยนสถานะ/ปิดงาน และสร้างรายงานต้องใช้ลำดับ lock ที่เข้ากันทุกเส้นทาง รวม client รุ่นเดิม/API/RPC และการเรียกซ้ำ
- ตรวจผลข้างเคียง helper ร่วมกับเริ่มนับเงิน: ห้ามสร้างวงจร “คิวพักเพราะนับเงินล็อก → เริ่มนับไม่ได้เพราะคิว” คงทางปลดล็อกชั่วคราวที่ผู้มีสิทธิ์ใช้จัดการงานก่อนนับตามเดิม ห้าม worker ปลดล็อกเอง
- งาน offline-only ไม่เป็น blocker ที่กลางตรวจพบได้ คง local guard ของเครื่องที่รู้ว่ามีงานยังไม่อัปโหลด ไม่อ้างว่าป้องกันได้ทั่วระบบก่อนข้อมูลถึงกลาง
- คิวว่างไม่ใช่คำสั่งให้สร้างรายงานเอง ต้องให้ผู้มีสิทธิ์กดสร้างตามเดิม

### การแจ้งและพิมพ์

- ผลสำเร็จจบเงียบ ปัญหาสาขาที่เปิดแจ้งสั้นไม่ซ้ำ command/reason; สาขาอื่นแสดงสถานะ/จำนวนเงียบ ๆ ไม่เปิด toast/dialog/หน้าบังล็อก/พิมพ์ ไม่เปลี่ยนหน้าหรือสาขา
- สถานะ/จำนวนคิวกลางและสิทธิ์จัดการต้องอ่านจาก Server ร่วมทุกเครื่อง ไม่พึ่ง local queue ของคนที่เปิดเพียงอย่างเดียว รวม local+central ด้วย command ID โดยไม่แสดงซ้ำ ตรวจสิทธิ์ก่อนแสดงและไม่อ้าง cache เป็นค่าล่าสุดขณะ offline
- หลังทิ้ง payload ให้เหลือเหตุขั้นต่ำสำหรับสถานะ/จำนวนและ terminal replay ไม่เก็บร่างเต็มเพียงเพื่อแจ้ง การเห็นปัญหาไม่ทำให้งานถูกส่งใหม่
- พิมพ์อัตโนมัติสร้างใหม่คงเดิม เฉพาะบัญชี/สาขาตรงเมื่อพร้อมและผ่าน print gate; ข้ามสาขาแล้วไม่เปิดและไม่พิมพ์ย้อนหลังเมื่อกลับมา รออนุมัติไม่พิมพ์
- แยก origin device/tab และ local print intent จากงานธุรกิจกลาง จัดลำดับบิลที่พร้อมหลายใบแทนการเรียก share ซ้อน ไม่พิมพ์ทุกเครื่องที่เห็นผลร่วมกัน
- การสร้าง/แชร์ PDF ล้มเหลว ถูกยกเลิก หรือเครื่องปิด ไม่ทำให้ส่งคำสั่งบิลซ้ำ ไม่รับประกัน browser exactly-once print ข้าม crash; เก็บ outcome ว่าได้เปิดส่งมอบแล้ว/ยังไม่พร้อมตามที่พิสูจน์ได้ และให้พิมพ์เองเมื่อจำเป็นโดยไม่เปิดย้อนหลังเอง

## สัญญาทางเทคนิคที่ต้องเสร็จก่อนเชื่อม UI

รายการต่อไปนี้เป็นข้อกำหนดให้จัดทำใน Phase 1 ไม่ใช่รายชื่อ table/endpoint ที่มีแล้ว และไม่ตรึง implementation โดยไม่มีหลักฐาน

1. **Action และ actor contract:** action matrix แยกสิทธิ์ดู/สร้าง/แก้/ลบ/retry/ทิ้ง/อนุมัติ/ลบคำขอ/OCR/ตั้งค่า ระบุ automatic vs ต้องกดยืนยัน ตรวจสิทธิ์ ณ รับงานและ ณ ประมวลผล และขอบเขตการจัดการแทนหลังถอนสิทธิ์ ห้ามตีความ generic “จัดการ” เป็นสิทธิ์อนุมัติ
2. **Identity และ lifecycle:** local persisted vs central accepted vs business terminal; immutable command ID/payload fingerprint/branch/actor/operation; semantic mapping ระหว่าง revision, generation และ queue version; อ่านผลเก่าก่อนพยายามทำใหม่ ไม่มีสอง active writers ต่อ logical bill
3. **Admission และลำดับต่อบิล:** กัน publish ซ้ำแม้คำตอบหาย กำหนดลำดับงานต่อบิลและ replacement ให้รักษาคำสั่งใหม่กว่า ห้ามเพิ่ม generation ตอน enqueue แล้วปล่อย worker ใช้ expected generation เก่าจนชนกับตัวเอง
4. **Typed outcome:** รหัสเหตุและ identity ที่ตรวจได้สำหรับ rejection/conflict/permission/cash-count/network ผลกำกวมคงคิว ไม่เดาจากข้อความ/HTTP 400/409 อย่างเดียว ทุก entry point ต้องใช้ contract เดียวกัน
5. **Atomic terminal และ retention:** ผลธุรกิจ+ผลคำสั่ง+เปลี่ยน blocker จบพร้อมกัน ล้างร่างเฉพาะ snapshot ปัจจุบันอย่าง conditional เก็บ minimal receipt/tombstone กัน replay ยาวกว่าประวัติแสดงผล; ไม่ลบ replay safety ตามการล้างประวัติชั่วคราวโดยไม่กำหนด compatibility
6. **เวลา ราคา และวันที่:** แยก client recorded, central accepted, executed และ business date ผู้ใช้ยืนยัน accepted-time สำหรับเงื่อนไขวันที่/ช่วงแก้ไขแล้ว: กลางออก accepted_at ครั้งเดียวเมื่อรับ command ถาวรสำเร็จ ใช้นาฬิกา Server และปฏิทิน Asia/Bangkok ไม่ใช้เวลา client ไม่เลื่อนเมื่อ retry/reopen/worker เปลี่ยน claim งาน offline-only ใช้เวลาที่กลางรับจริงเมื่อออนไลน์ ไม่ backdate accepted_at หรือแก้ billDate/clientRecordedAt ตามเวลา worker สิทธิ์/ล็อก/revision ตรวจตอน execute; ระบบกลางต้องตรวจและบันทึก authoritative price-policy snapshot ที่รับงาน (central price, allowance, cap, rule source/revision และผลตรวจราคา) แล้ว worker ใช้ snapshot เดิมกับคำสั่งเดิม แม้เพดานลดหลังรับแล้ว ห้ามแก้ราคาที่ผู้ใช้กรอกหรือเพิ่มอนุมัติเพียงเพราะคิวช้า งานที่ต้องอนุมัติตั้งแต่รับยังรออนุมัติตามเดิม งาน offline ใช้กฎจริงเมื่อกลางรับ ไม่เชื่อ client cache แทน Server snapshot; retry ไม่สร้าง snapshot ใหม่ แต่ correction/new intent ตรวจใหม่ รุ่นเก่าที่ไม่มี snapshot ที่เชื่อถือได้ห้ามเดาย้อนว่าผ่านแล้ว ต้องใช้ compatibility contract ทดสอบข้ามวัน/ช่วงแก้ไข/ราคาเปลี่ยนระหว่างรอ พร้อม recheck สิทธิ์/ล็อก/revision ก่อนธุรกิจจริง
7. **Worker และปฏิบัติการ:** เลือกจากกลไก DB/pg_cron เดิมก่อนเพิ่ม framework; transaction/claim fence ที่กันหลาย worker และ late result; batch จำกัด, fairness ข้ามสาขา, retry backoff, timeout/stale-running recovery, bounded errors, restart safety, metrics และวิธีปลุกเมื่อปลดล็อก/คืนสิทธิ์ กำหนดเกณฑ์ความเร็วรับงาน/ทำงานด้วยการวัดก่อน release ไม่อ้างว่า cron ทุกนาทีเท่ากับทันที
8. **Shared read contract:** feed/cursor/order/search/count/action permission พร้อม dedup local/central และ refresh policy รวมคำตอบที่ถูกต้องเมื่อ worker จบโดยไม่มี browser sender มา invalidate cache

## สิ่งที่ลดและสิ่งที่คง

ลดตัวประมวลผลข้ามสาขา/รับช่วงฝั่ง browser สำหรับคำสั่งรุ่นใหม่เหลือ uploader/result reconciliation; คง sender เก่าเฉพาะ compatibility ที่ระบุ marker ชัดและไม่แข่งคิวกลาง คง context/RPC การคำนวณสูตรเงิน generation/receipt/approval/replacement/OCR guards ที่ใช้ได้ ไม่สร้าง rule engine หรือ job framework ใหม่โดยไม่จำเป็น

ไม่ยืมนโยบายรับ–จ่ายโดยอัตโนมัติ แม้ source ร่วมกำลังเปลี่ยนจากแชตอื่น ต้องอ่าน diff สดของ coordinator, auth-fetch, IndexedDB version/stores, retry และ tests ก่อนเชื่อม งานรับ–จ่าย/attachments ของผู้อื่นห้าม revert/stage รวม

## ขอบเขตการยืนยันและประวัติย่อ

- ปัจจุบันยืนยันผลิตภัณฑ์และการปรับแผนแล้ว ไม่มี source/test/DB/deployment evidence ของคิวกลางใหม่ งานทั้งหมดรอคำสั่งเริ่ม
- กฎก่อนหน้าที่ให้ browser เครื่องอื่นเป็นตัวส่งหลัก ถูกแทนด้วย server worker; คงทุกเครื่องเห็นและจัดการข้อยกเว้นตามสิทธิ์
- กฎที่เคยให้แจ้งหรือพิมพ์ข้ามสาขาถูกแทนด้วย silent off-branch และไม่พิมพ์ย้อนหลัง
- กฎเก็บร่าง conflict ของ ADR-0083 เดิมจะมีข้อยกเว้นใหม่ที่ผู้ใช้ยืนยันในแชตนี้ ต้องบันทึก successor ADR หลังเริ่มและมี contract ไม่แก้ความหมายหลักฐาน rollout เดิมให้เหมือน implementation ใหม่มีแล้ว
- accepted-time สำหรับวันที่/ช่วงแก้ไขและกติการาคาที่กลางตรวจผ่าน ณ รับงานได้รับยืนยันแล้ว ต้อง implement เป็น contract รุ่นใหม่และตรวจ regression สิทธิ์กระทำแทน/OCR/action ที่ยังไม่ยืนยันเป็น decision gate ใน Phase 1 ห้ามเริ่มส่วนที่พึ่งคำตอบนั้นจนตกลง
