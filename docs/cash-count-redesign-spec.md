# ข้อกำหนดหลัก: ปรับระบบนับเงิน

วันที่สรุป: 24 ตุลาคม 2569

เอกสารนี้รวบรวมข้อตกลงจากการสัมภาษณ์และข้อแก้ไขล่าสุดของผู้ใช้ เป็นข้อกำหนดสำหรับพัฒนา ไม่ใช่หลักฐานว่าระบบได้เปลี่ยนแล้ว หากเอกสารออกแบบเดิมขัดกัน ให้ใช้ข้อกำหนดใหม่ฉบับนี้สำหรับงานปรับระบบนับเงิน

## 1. แยกนับเงินออกจากรายงาน

- Route/โมดูลนับเงินและรายการรายงานทำงานแยกกัน การนับเงินไม่สร้างรายงาน ไม่ผูกรายงาน และไม่สร้าง Report Lock
- การลบนับเงินไม่ลบรายงาน การลบรายงานไม่ลบนับเงิน
- นำคอลัมน์ “จริง / คาดการณ์” และ “ผลวิเคราะห์” ออก รวมถึงการคาดการณ์แยกชนิดธนบัตร คะแนนความผิดปกติ ความเชื่อมั่น และโค้ด/API/ฟังก์ชัน/การทดสอบที่ใช้เฉพาะกลไกเหล่านี้
- ยกเลิกการตั้งฐานอัตโนมัติที่ทำให้ยอดคาดการณ์เท่ากับยอดนับและกลบส่วนต่าง
- ใช้โครงสร้างรอบนับเดิมและสิทธิ์เดิมที่ยังเกี่ยวข้อง โดยถอดการพึ่งพารายงานออก และเพิ่มการบังคับหยุดเคลื่อนไหวฝั่งฐานข้อมูลให้ครบ ไม่ถือว่าตัวล็อกธุรกรรมเดิมหยุดการเงินได้ตลอดรอบ

## 2. เริ่มนับและตรึงยอด

- เมื่อกดเริ่มนับ ตรึงยอดรับ–จ่ายสุทธิสะสมของสาขาพร้อมเวลาเริ่มนับจากระบบส่วนกลาง
- ใช้สูตรรับ–จ่ายสุทธิสะสมเดียวกับภาพรวมสาขา ไม่สร้างสูตรยอดเงินอีกชุด คำนวณจากข้อมูลจริงหลังผ่านจุดล็อกร่วม ไม่คัดลอกยอด snapshot ที่อาจค้าง และไม่จำเป็นต้องสร้างภาพรวมทั้งหมดใหม่
- บังคับหยุดทุกคำสั่งที่เปลี่ยนยอดของสาขาระหว่างรอบนับ รวมการเพิ่ม แก้ ลบ อนุมัติ รับโอน และงานเบื้องหลังที่เกี่ยวข้อง ตรวจจากทุกอุปกรณ์ และจัดลำดับล็อกสำหรับคำสั่งหลายสาขาให้เหมือนกัน คงเฉพาะเงื่อนไขงานค้างที่จำเป็นต่อความถูกต้องของยอด
- ถอดเงื่อนไขต้องมีรายการพร้อมออกรายงาน สาขาที่ไม่มีรายการใหม่หรือเพิ่งออกรายงานต้องเริ่มนับได้
- คงรอบนับเดิมสูงสุด 30 นาที ปลดล็อกเมื่อบันทึกสำเร็จ ยกเลิก หรือหมดเวลา
- หากต้องเคลื่อนไหวเงินจริงระหว่างนับ ให้ยกเลิกแล้วเริ่มรอบใหม่ ห้ามส่งผลด้วยรอบที่หมดเวลาแล้ว
- ไม่ใช้ยอดระบบ ณ เวลาส่งผลมาแทนยอดที่ตรึงตอนเริ่มนับ และไม่เปลี่ยนยอดฐานในประวัติตามยอดปัจจุบัน

## 3. เงินสดและการคำนวณ

- กรอกจำนวนธนบัตร 1,000 / 500 / 100 / 50 / 20 บาท และเหรียญ 10 / 5 / 2 / 1 บาท ใช้รายละเอียดการนับเดิม
- เงินสดรวม = ผลรวมของมูลค่าเงินแต่ละชนิดคูณจำนวน
- ยอดนับรวม = เงินสดรวม + เงินในบัญชี
- ส่วนต่าง = ยอดนับรวม − ยอดระบบ ณ เริ่มนับ
- ส่วนต่างติดลบแสดงเงินขาด เป็นบวกแสดงเงินเกิน และศูนย์แสดงยอดตรงกัน
- ยอดต่างบันทึกได้ ไม่มีช่องเหตุผลทั้งในฟอร์มและ PDF และไม่ปรับยอดรับ–จ่ายอัตโนมัติ
- หากพบต้นทางตกหล่น ให้แก้ต้นทางและนับใหม่
- ตัวอย่าง: เงินสด 70,000 + เงินในบัญชี 29,500 − ยอดระบบ 100,000 = เงินขาด 500 บาท

## 4. เงินในบัญชีและกล้อง OCR

- หนึ่งรายการนับเงินมีได้ 0–4 บัญชี ช่องละหนึ่งรูป ยอมให้บัญชีและรูปซ้ำกันได้ ไม่ตรวจชื่อธนาคารหรือเลขท้าย ตามข้อตกลงขยายล่าสุด
- บัญชีเป็นทางเลือก สาขาที่ไม่ใช้บัญชีคำนวณส่วนนี้เป็นศูนย์
- รับรูปจากการถ่ายกล้องเท่านั้น ไม่มีการแนบรูปจากคลังหรือเลือกไฟล์
- รายละเอียดบัญชีในหน้าจอมีเฉพาะยอดเงินแบบ readonly ไม่ให้แก้ยอดด้วยมือ
- ถ่ายซ้ำได้แยกช่อง โดยรูปใหม่แทนรูปเดิมของช่องนั้น
- OCR อ่านยอดคงเหลือเป็นหลัก หากมีเฉพาะยอดเงินที่ใช้ได้จึงใช้ยอดนั้น หากมีทั้งสองยอดและต่างกันให้เลือกยอดคงเหลือ
- มองหาการ์ดบัญชีช่วงบนของหน้าจอตามภาพตัวอย่าง แต่ไม่ใช้ขนาดหรือตำแหน่งตัวเลขเพียงอย่างเดียวตัดสิน
- ไม่อ่านยอดธุรกรรม วงเงิน อัตราดอกเบี้ย เลขบัญชี หรือบวกยอดรวมกับยอดบัญชีซ้ำ
- หากหลายบัญชี เลือกยอดไม่ได้ ยอดถูกซ่อน หรือเลขไม่ชัด ให้คืนผลอ่านไม่สำเร็จ ห้ามเดาและห้ามบันทึก
- แสดงรูปคู่กับยอด OCR ให้ผู้ใช้ยืนยัน “ยอดตรงกับรูป” ก่อนบันทึก หากผิดต้องถ่ายใหม่ และทุกครั้งที่ถ่ายใหม่ต้องยืนยันใหม่
- หากอ่านไม่สำเร็จ ผู้ใช้เลือกไม่นำเงินในบัญชีมารวมได้ แต่ต้องยืนยันชัดเจนก่อนล้างรูปและใช้ยอดบัญชีศูนย์ ห้ามระบบแปลง OCR ที่ล้มเหลวเป็นศูนย์เอง

### ร่างคำสั่ง OCR แบบกระชับ

อ่านยอดบัญชีธนาคารเดียวจากภาพถ่ายจอ เลือกยอดคงเหลือก่อน; ใช้ยอดใช้ได้เมื่อไม่มียอดคงเหลือ มองหาการ์ดบัญชีช่วงบน แต่อย่าเลือกจากขนาดหรือตำแหน่งอย่างเดียว ไม่อ่านยอดธุรกรรม วงเงิน เลขบัญชี หรือบวกยอดซ้ำ หากหลายบัญชี เลือกยอดไม่ได้ ยอดซ่อน หรือเลขไม่ชัด ให้ amount=null ห้ามเดา คืน JSON เท่านั้น: {"amount":"1234.56"|null,"kind":"balance"|"available"|null}

คำสั่งนี้เป็นร่างสำหรับทดสอบ ต้องทดสอบกับภาพตัวอย่างทั้งหกและภาพอ่านไม่ได้ก่อนใช้งานจริง โดยไม่ถือว่าขนาดตัวเลขเพียงอย่างเดียวรับประกันความแม่นยำ

## 5. Google Drive และการลองใหม่

- ใช้แนวทางจัดเก็บ Google Drive เดียวกับ OCR ใบชั่ง
- เก็บรูปสุดท้ายที่ใช้บันทึกจริงหนึ่งรูปต่อบัญชี สูงสุดสี่รูปต่อรายการ ไม่เก็บภาพถ่ายซ้ำทุกครั้งเป็นหลักฐานของรายการ
- หากมีบัญชี รูปทุกช่องต้องบันทึกลง Drive สำเร็จก่อนถือว่าบันทึกรายการสำเร็จ ลองใหม่เฉพาะรูปที่ยังไม่สำเร็จ
- หากอัปโหลดล้มเหลว บล็อกการบันทึก พร้อมให้ลองใหม่โดยคงยอดนับและรูปไว้ระหว่างรอบที่ยังไม่หมดเวลา ไม่บังคับถ่ายใหม่เพราะอัปโหลดล้มเหลว
- การลองใหม่ต้องไม่สร้างรายการนับซ้ำหรือหลักฐานซ้ำของรายการเดียว
- แยกจังหวะ OCR กับเก็บรูปสุดท้าย ไม่คัดลอกวงจรอัปโหลดทุกภาพของใบชั่งมาทั้งชุด ผูกผลอ่านกับรูป ผู้ใช้ สาขา และรอบนับฝั่งเซิร์ฟเวอร์ ไม่เชื่อยอดที่ส่งจากหน้าจอโดยลำพัง
- ต้องมีขั้นกู้คืนเมื่อ Drive สำเร็จแต่ฐานข้อมูลล้มเหลวหรือคำตอบสูญหาย และจัดการรูปที่ไม่ถูกใช้โดยไม่ลบหลักฐานที่บันทึกสำเร็จแล้ว

## 6. ประวัติ การลบ และการตรวจสอบ

- เก็บประวัตินับเงินเดิม แต่ถอดความผูกพันกับรายงานและเลิกแสดงผลคาดการณ์/วิเคราะห์เดิม
- ไม่สร้างยอดระบบย้อนหลังในรายการเก่าที่ไม่มีหลักฐาน
- รายการบันทึกแล้วดูรายละเอียดและลบตามสิทธิ์เดิมได้ แต่แก้ยอดย้อนหลังไม่ได้ หากนับผิดให้ลบแล้วเริ่มใหม่
- เพิ่มปุ่ม “ยืนยันตรวจสอบ” เป็นทางเลือก ไม่จำเป็นต้องกดทุกรายการ และไม่ขวางการบันทึกหรือการเริ่มรอบแจ้งเตือนใหม่
- ผู้มองเห็นและกดปุ่มตรวจสอบใช้ `canManageSystemFeatures`: Super Admin หรือ Admin ที่มี `canAccessSystemManager` ตามสิทธิ์แท็บจัดการระบบใน Admin ไม่ใช่ Admin ทุกบัญชี
- แสดงชื่อผู้กดยืนยันตรวจสอบในรายละเอียด
- แนวทาง implementation จากผลรีวิว: ยืนยันครั้งเดียวแบบกดซ้ำได้โดยไม่เปลี่ยนชื่อผู้ตรวจคนแรก เก็บเวลาตรวจด้วย และจัดการการกดพร้อมกัน/การลบพร้อมกันอย่างชัดเจน
- ตรวจสอบแล้วก็ยังลบตามสิทธิ์เดิมได้ ไม่เพิ่มขั้นอนุมัติหรือการล็อกเพราะการตรวจสอบ
- รายการใหม่ใช้เลขใบนับเงินอิสระ ปรับประวัติการลบและถอดลิงก์นับเงินจากหน้ารายงาน เลขอ้างอิงเดิมเก็บเพื่ออ่านประวัติได้แต่ไม่ใช้ผูกการลบ

## 7. PDF ใบนับเงิน 80 มม.

- รองรับพิมพ์ PDF หน้ากว้าง 80 มม. ใช้รูปแบบเดียวกับเอกสารเงินเดือนที่มีอยู่
- มีข้อมูลระบุรายการ สาขา เวลาเริ่มนับ และเวลาบันทึก
- แสดงชนิดเงิน จำนวน และยอดรวมรายชนิด พร้อมยอดเงินสดรวม
- แสดงบัญชี 1–4 พร้อมยอดรายช่องและยอดบัญชีรวม ยอดนับรวม ยอดระบบ ณ เริ่มนับ และจำนวนเงินขาด/เกิน/ตรงกัน
- กรณีไม่ใช้บัญชี แสดงว่าไม่นำเงินในบัญชีมารวม และคำนวณเป็นศูนย์
- ไม่มีส่วนเหตุผล
- ด้านล่างมีบรรทัดเซ็นผู้นับและผู้ตรวจ พร้อมชื่อใต้บรรทัด
- พิมพ์ได้ก่อนยืนยันตรวจสอบ โดยเว้นชื่อผู้ตรวจให้เขียนเอง หากตรวจสอบแล้วให้แสดงชื่อผู้กดยืนยัน
- รายการเก่าที่ไม่มีข้อมูลยอดระบบต้องแสดงว่าไม่มีข้อมูล ไม่สร้างส่วนต่างขึ้นจากยอดฐานที่ไม่ทราบ

## 8. กลุ่มเกณฑ์นับเงินใน Admin

- เพิ่มการตั้งกลุ่มเกณฑ์นับเงินใน Admin ส่วน “การแจ้งเตือน”
- กลุ่มนับเงินแยกสมาชิกและเกณฑ์จากกลุ่มแจ้งเตือนเงินต่ำและน้ำหนัก
- แต่ละสาขาอยู่ได้ไม่เกินหนึ่งกลุ่มนับเงิน แต่ละกลุ่มใช้ระยะกำหนดร่วมกัน 1–5 วัน
- สาขานอกกลุ่มไม่มีการแจ้งเตือนนับเงินและไม่มีเกณฑ์สำรอง
- ใช้วันปฏิทินตามเวลาไทยจากวันที่นับล่าสุดที่ยังไม่ถูกลบ หากไม่มีรายการให้ใช้วันที่เข้ากลุ่ม
- ใช้วันเริ่มนับตาม cutoff ของรายการที่บันทึกสำเร็จเป็นวันที่นับ ต้องทดสอบเริ่มก่อนเที่ยงคืนและส่งผลหลังเที่ยงคืน
- วันครบกำหนดยังไม่ถือว่าล่าช้า เริ่มเตือนในวันถัดไป พร้อมจำนวนวันที่เลยกำหนด
- ตัวอย่าง: ล่าสุดวันที่ 24 ต.ค. เกณฑ์ 2 วัน ครบกำหนด 26 ต.ค. และวันที่ 27 ต.ค. แจ้งล่าช้า 1 วัน
- บันทึกสำเร็จถือว่านับแล้วแม้ยอดขาดหรือเกิน และไม่ต้องรอยืนยันตรวจสอบจึงเริ่มรอบใหม่
- เริ่มนับเฉย ๆ ยกเลิก หรือหมดเวลา ไม่ถือว่านับสำเร็จ
- ลบรายการล่าสุดแล้วใช้รายการก่อนหน้าที่ยังไม่ลบ หากไม่เหลือให้ใช้วันเข้ากลุ่ม จึงอาจกลับมาแจ้งเตือนทันที
- ใช้วันที่นับของประวัติเดิมที่ยังไม่ลบเป็นฐานได้
- เปลี่ยนเกณฑ์หรือย้ายกลุ่มให้ใช้เกณฑ์ใหม่ทันที สาขาที่เคยนับยึดวันที่นับล่าสุดเดิม
- สาขาที่ยังไม่เคยนับ เมื่อย้ายกลุ่มให้เริ่มระยะใหม่จากวันที่เข้ากลุ่มใหม่

## 9. หน้าต่างแจ้งเตือนร่วมและสิทธิ์

- ใช้หน้าต่างร่วมกับเงินต่ำและน้ำหนัก มีปุ่มเลือก “นับเงิน” แยกเฉพาะ
- ส่วนรายการใช้ `mt-4 max-h-[min(50dvh,24rem)] space-y-3 overflow-y-auto pr-1`
- ปุ่มใช้ `focus-ring min-h-11 rounded-md border px-3 text-sm font-semibold border-black/15 bg-white`
- ใช้รอบตรวจอัตโนมัติเดิมร่วมกัน กดรับทราบปิดหน้าต่างทั้งรอบ
- รอบถัดไปเตือนซ้ำหากยังเกินกำหนด พร้อมระยะล่าช้าล่าสุด
- ปุ่มตรวจแจ้งเตือนด้วยตนเองตรวจนับเงินด้วย โดยรักษาพฤติกรรมรอบอัตโนมัติเดิม
- Admin รับเฉพาะสาขาที่ได้รับมอบหมาย ผู้จัดการระบบและ Super Admin รับทุกสาขาที่เปิดใช้งาน User ไม่รับแจ้งเตือนนี้
- สิทธิ์รับแจ้งเตือนและสิทธิ์ยืนยันตรวจสอบเป็นคนละสิทธิ์ตามข้างต้น
- เพิ่มประเภทนับเงินในสัญญาแจ้งเตือนร่วมเดิม คำนวณจากรายการนับและสมาชิกกลุ่มโดยตรง ไม่พึ่งความพร้อมของ snapshot เงิน/น้ำหนัก และไม่เพิ่มตัวตั้งเวลาอีกชุด

## ลำดับดำเนินงานหลังรีวิว

1. ยืนยันเส้นทางยอดเงินจริง จุดหยุดเคลื่อนไหว และสัญญาข้อมูล
2. ทำฐานข้อมูล/API และแยกรายงาน พร้อมทดสอบการทำงานพร้อมกัน
3. ทำฟอร์มนับเงินและ OCR/Drive ให้จบครบหนึ่งรายการ
4. เพิ่มตรวจสอบและ PDF โดยใช้เครื่องมือเดิม
5. เพิ่มกลุ่มและแจ้งเตือนในระบบร่วมเดิม
6. ตรวจย้อนหลังและ regression แล้วจึงล้างโค้ดเก่าและเตรียมส่งมอบ

ใช้ migration ใหม่เท่านั้น ไม่แก้ migration ที่ใช้ไปแล้ว ถอด consumer และจุดเชื่อมทั้งหมดก่อนลบฟังก์ชัน/คอลัมน์เก่า โดยเฉพาะฟังก์ชันคำนวณที่มีเส้นทางเงินเดือนห่ออยู่ คงข้อมูลเก่าที่จำเป็นต่อประวัติ ไม่ขยายโมดูลเงินเดือนเพียงเพื่อทำ PDF ใบนับเงิน

## 10. เกณฑ์ตรวจรับ

- นับและลบได้โดยไม่สร้างหรือลบรายงาน ไม่มีการคาดการณ์/วิเคราะห์เดิมในขั้นตอนใหม่
- ยอดระบบตรึงตอนเริ่มนับ สูตรรวมและส่วนต่างถูกต้อง และการนับไม่เปลี่ยนรับ–จ่าย
- ทดสอบเงินขาด เกิน ตรงกัน และไม่ใช้บัญชี โดยไม่มีช่องเหตุผล
- ภาพชัดอ่านยอดได้ถูกต้อง ภาพกำกวมหรือซ่อนยอดบันทึกไม่ได้ ถ่ายใหม่ล้างการยืนยันเดิม และยอด OCR แก้ด้วยมือไม่ได้
- Drive ล้มเหลวบันทึกไม่ได้ ลองใหม่ไม่เกิดรายการซ้ำ และรอบหมดเวลาใช้งานต่อไม่ได้
- สิทธิ์ตรวจสอบถูกต้อง แสดงชื่อผู้ตรวจ ไม่บังคับตรวจ และตรวจแล้วลบตามสิทธิ์เดิมได้
- PDF ภาษาไทยอ่านได้บนหน้ากว้าง 80 มม. รายละเอียดครบ ไม่ล้น มีบรรทัดเซ็น และพิมพ์ก่อนตรวจสอบได้
- ตรวจแจ้งเตือนวันครบกำหนด วันล่าช้า สาขาไม่มีประวัติ การย้ายกลุ่ม เปลี่ยนเกณฑ์ ลบรายการ และสาขานอกกลุ่ม
- ตรวจสิทธิ์ผู้รับ หน้าต่างร่วม การรับทราบ และการเตือนซ้ำไม่รบกวนเงินต่ำ/น้ำหนักเดิม
- ประวัติและรายงานเดิมยังเข้าถึงได้โดยไม่สร้างข้อมูลย้อนหลังที่ไม่มีหลักฐาน

## ขอบเขตหลายบัญชีที่ใช้แทนข้อจำกัดหนึ่งบัญชีเดิม

เพิ่มช่องได้สูงสุดสี่ ไม่บังคับมีบัญชี หากช่องใดยังไม่ถ่าย อ่านไม่ชัด หรือยังไม่ยืนยัน จะบันทึกทั้งรายการไม่ได้จนกว่าจะถ่าย/ยืนยันหรือนำช่องนั้นออก ไม่ข้ามเงียบ ๆ และไม่กรอกธนาคารหรือชื่อบัญชี รูปเปิดดูแยกช่องในรายละเอียด ไม่ใส่ใน PDF รายการหนึ่งบัญชีเดิมคงเป็นบัญชี 1 ดู docs/cash-count-multi-account-design.md

รูปแบบแสดงล่าสุดที่ผู้ใช้ยืนยัน: `บัญชี1 = 10,000.00 บาท` ไล่ตามจำนวนจริงถึงบัญชี4 ทั้งฟอร์ม รายละเอียด และ PDF ไม่ใช้ตัว N เป็นข้อความบนหน้าจอ
