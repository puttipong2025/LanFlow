# แผนดำเนินงาน — อัปเดตแคชบิลยางและรับ–จ่าย

สถานะ: พัฒนาและตรวจรับครบ 4 Phase / ติดตั้ง migration บน Supabase Cloud แล้วตามคำสั่งเผยแพร่ 2026-10-30
วันที่ทบทวน: 2026-10-30

## เป้าหมายและข้อจำกัดของหลักฐาน

จัดการสำเนาข้อมูลเก่าของบิลยางและรับ–จ่ายตามเวอร์ชัน โดยใช้ระบบโหลดข้อมูลเดิม รักษางานที่ยังไม่จบ และแสดงสถานะในกรอบความพร้อมออฟไลน์เดิม

ผู้ใช้รายงานว่ารายการที่เคยลบกลับมาเมื่อเพิ่ม แก้ไข หรือลบบิลยางออฟไลน์ และล้างแคชเองแล้วอาการหาย ยังไม่ยืนยันต้นเหตุหรือทำอาการจริงซ้ำได้สำเร็จ ต้องแยก **การอัปเกรดแคชเมื่อเปลี่ยนรุ่น** ออกจาก **การรักษาสถานะบิลที่ลบตามการทำงานปกติ** เพราะบิลอาจถูกลบโดยเวอร์ชันแคชไม่เปลี่ยน ห้ามใช้ผลอัปเกรดแคชแทนหลักฐานแก้บั๊กเดิม

## ข้อตกลงจากผู้ใช้

- ครอบคลุมบิลยางและรับ–จ่ายทุกเครื่อง โดยทำงานเมื่อเปิดเว็บออนไลน์หรือกลับมาออนไลน์ ไม่ทำงานขณะปิดเว็บ
- ตรวจเลขเวอร์ชันตอนเปิดหน้า/โหลดใหม่/F5 ขณะออนไลน์ และออฟไลน์กลับมาออนไลน์เสมอ เพิ่มรอบตรวจค่ากลาง 10–120 นาทีที่ superadmin เปิดได้ (ค่าเริ่มต้นปิด) เฉพาะออนไลน์และแท็บมองเห็น ไม่มีการตรวจทันทีเมื่อกลับเข้าแท็บ และปุ่มตรวจความพร้อมเดิมไม่ใช่ trigger เวอร์ชัน
- เปลี่ยนเลขเวอร์ชันเฉพาะเมื่อจำเป็น ไม่ใช้ build ID ไม่ล้างทุก deployment รุ่นเท่าเดิมไม่เริ่มเปลี่ยนชุดแคชจากกลไกนี้ การโหลดและซิงก์งานปกติยังทำงานตามเดิม
- เตรียมชุดทดแทนก่อนเปลี่ยน หากไม่ครบหรือผิดพลาดใช้ชุดเดิมต่อ ไม่ล้างจนตารางว่าง
- เก็บงานไม่เคยส่ง ส่งแล้วไม่ทราบผล เซิร์ฟเวอร์รับแล้วรอประมวลผล failed conflict และรออนุมัติ รวมหลักฐานลบ/ยืนยันผลและผลแจ้งที่ยังจำเป็น โดยไม่เปลี่ยนกติกาการจบคำสั่งเดิม
- ฟอร์มใช้พฤติกรรมเดิม ไม่เพิ่ม persistent draft ให้บิลยาง รอให้บันทึกหรือปิดฟอร์มก่อนเปลี่ยนข้อมูลที่กระทบฟอร์ม F5 ที่ผู้ใช้กดเองยังมีพฤติกรรมเดิม
- ระบบประสานหลายแท็บเอง ไม่ให้ผู้ใช้ไล่ปิดทุกแท็บ รักษา Auth สิทธิ์ การเลือกสาขา และข้อมูลโมดูลอื่น
- หน้าตา **รายละเอียดแยกส่วน** ตามคำสั่งเลือกแบบล่าสุด ในกรอบ `max-w-xs rounded-lg border border-mint bg-white px-3 py-2 text-xs text-ink` ไม่ใช้แบบสรุปกระชับจากสถานะตัวอย่างที่อาจยังค้าง
- เครื่องออนไลน์เปิดค้างตรวจเพิ่มตามรอบค่ากลางได้ เมื่อปิดรอบตรวจจะรอเปิด/โหลดหน้าใหม่หรือกลับมาออนไลน์ สถานะรุ่นแคชตรงกันไม่ยืนยันว่าข้อมูลธุรกิจทุกบิลสดล่าสุด

## สัญญาที่ต้องตรึงก่อนเขียนโค้ด

### Metadata และชุดข้อมูลทดแทน

- ใช้จุดอ่าน metadata เล็กจุดเดียวสำหรับสองโมดูล มีรุ่นแยกโมดูล ใช้ authorization ตาม API เดิมและ `private, no-store` ไม่คืนข้อมูลธุรกิจจากจุดนี้
- รุ่นนี้เป็นรุ่นวิธีเก็บ/อ่านสำเนา ไม่ใช่ตัวนับการเพิ่มแก้ลบบิล หากยังไม่มีรุ่นในเครื่องต้องตรวจและเตรียมขอบเขตที่เกี่ยวข้องก่อนรับรุ่นใหม่ ห้ามแค่เขียนเลขแล้วถือว่าสำเร็จ
- บิลยาง: จับรายการ ID/revision ของสำเนาที่ตั้งใจตรวจ ขอข้อมูลเป็นชุดไม่เกิน 100 ID ต่อคำขอ หรือขีดจำกัดที่ยืนยันจากระบบจริง หากมากกว่านั้นแบ่งชุดและจำกัด concurrency ไม่เรียกทีละบิล ไม่โหลดประวัติทั้งหมด/ทุกสาขา
- กำหนด response ต่อ ID/สาขาเป็น active พร้อม revision/ข้อมูลทดแทน, positively deleted, unknown/not-found, forbidden และ error การหายจากหน้าแรก ผลค้นหา หรือ response ว่างไม่ใช่หลักฐานลบ
- ใช้ feed ปกติที่กำลังโหลดร่วมได้ แต่ชุดทดแทนต้องครอบคลุม ID เดิมที่ตั้งใจแทนที่ หากต้องเพิ่ม batch API/RPC ให้ตรึง request/response, authorization/RLS, limit, timeout และ errors ก่อนพัฒนา ใช้ของเดิมหากทำครบได้
- หากมี unknown/forbidden/error ในชุดที่ตั้งใจแทนที่ ห้าม commit ชุดนั้นหรือรับรุ่นใหม่ และห้ามสร้างเครื่องหมายลบจากความไม่ทราบผล
- คิว ผลแจ้ง draft และหลักฐานยืนยันผล/ลบไม่ใช่ข้อมูลทดแทนจาก endpoint นี้

### Commit ขอบเขตข้อมูล และแท็บรุ่นเก่า

- เตรียมข้อมูลนอก transaction แล้วเปิด transaction สั้นเพื่อตรวจสถานะล่าสุดและเปลี่ยนสำเนา/รุ่น/เวลาสำเร็จพร้อมกัน Metadata ของสำเนาถาวรต้องอยู่ใน transaction เดียวกันได้ ไม่เขียนคนละ storage โดยไม่มีวิธีกู้คืนที่พิสูจน์ได้
- ตรวจคิว หลักฐานลบ และ revision ล่าสุดตอน commit ไม่เขียนทับบิลที่ซิงก์ใหม่กว่าระหว่างโหลดชุดใหม่ Prune ต้องตรวจเงื่อนไขกับ snapshot ปัจจุบัน ไม่ลบจากผลอ่านเก่าอย่างเดียว
- แยกความสำเร็จต่อโมดูล/สาขา เปลี่ยนบัญชีหรือสิทธิ์แล้วต้องไม่เผยแพร่ผลจาก session เดิมเข้าสู่ UI ใหม่
- เพิ่มตัวตรวจรุ่นเฉพาะโค้ดใหม่ไม่ป้องกันโค้ดเก่าที่ไม่รู้จักตัวตรวจ ต้องตรึงนโยบาย mixed-client ก่อนเพิ่ม schema/store/generation
- หากเลือก IndexedDB version fence ต้องทดสอบปิด connection, old reopen, ข้อความให้โหลดแอปใหม่ และ rollback ที่ไม่ลด DB version ห้ามล้างฐานข้อมูลเพื่อแก้ compatibility และห้ามรับประกันแท็บเก่าทุกเวอร์ชันโดยไม่มีหลักฐาน
- ใช้กลไกเล็กที่สุดที่ทำสัญญานี้ได้ ไม่สร้าง snapshot/generation framework กลางสำหรับทุกโมดูลโดยไม่มีความจำเป็น

### ลำดับกลับมาออนไลน์

1. ยืนยัน session/สิทธิ์/สาขา รวมเหตุเปิดหน้า/reconnect ที่ติดกันเข้าการตรวจเดียวใน scope ที่เกี่ยวข้อง
2. ตัวซิงก์เดิมยังยืนยันผลงานได้ ไม่รอให้คิวว่างและไม่ถือว่าคำขอค้างถูกยกเลิก
3. ตรวจ metadata รุ่นเดิมจบเฉพาะการตรวจรุ่น รุ่นต่างจึงเตรียมข้อมูลตามโมดูล ประสาน feed ปกติไม่ให้โหลดซ้ำ
4. รอฟอร์มที่กระทบก่อนเปลี่ยน ประสาน reconnect reload เดิมให้เคารพกติกานี้ ไม่เพิ่ม reload จากตัวตรวจใหม่โดยไม่จำเป็น
5. ตรวจความเป็นปัจจุบันอีกครั้งและ commit แล้วจึงเผยแพร่สถานะ/เวลา อีกโมดูลหรือสาขาไม่สำเร็จตามโดยอัตโนมัติ
6. ผิดพลาดใช้ชุดเดิมและแสดงล้มเหลว ไม่เพิ่ม retry ไม่จำกัด ใช้รอบค่ากลางเมื่อเปิดไว้หรือ ลองตรวจใหม่ที่ trigger ที่ผู้ใช้เลือกครั้งถัดไป การรอปิดฟอร์มและทำต่อจากข้อมูลที่เตรียมไว้ไม่ใช่ trigger ตรวจรุ่นใหม่

ถ้าสิทธิ์ถูกถอนต้องใช้การป้องกันเข้าถึงเดิม ไม่แสดงข้อมูลที่ไม่มีสิทธิ์เพียงเพราะนโยบายคงชุดเดิม
