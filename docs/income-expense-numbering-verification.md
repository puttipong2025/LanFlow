# Income/Expense device numbering — implementation and verification

Current form policy: [ADR 0098](adr/0098-income-expense-fresh-create-forms.md) supersedes the partial-form recovery described in this historical verification. New forms discard unfinished input; accepted numbered work and replay protection remain durable.

Started: 2026-11-01. User authorized all four phases of the 32-task vault plan. Scope remains general income/expense creates; rubber, legacy commands, sales and derived sources retain their contracts. Work is Local; no Cloud migration, commit, push or deployment is part of this run.

## Implementation decisions

- Reuse the existing browser/profile/branch issuer registration. Its durable root contains separate I/E counters and reservations, with an explicit initialization marker. Invalid or missing previously initialized numbering state requires online registration under a fresh code. Rubber counters and existing commands are preserved by the IndexedDB v10 upgrade.
- A local acceptance transaction owns the counter, reservation, immutable accepted-row snapshot and outbox record. Row identity is the persisted form-line identity. Reopening or retrying a partially accepted form retrieves the original snapshot instead of issuing another number.
- New general creates use the existing Income/Expense sync path, which already applies authoritative approval rules. A dedicated numbered RPC fences older servers. Local offline restrictions still run before acceptance. Existing queued legacy creates retain their old number on edit.
- The existing business core allocates the final suffix immediately before INSERT in its exception scope. A forced INSERT failure rolls back the number binding and suffix counter together. Both direct creation and approval use that core.
- Durable create receipts preserve the original fingerprint and pending/final/rejected outcome across approval-history cleanup. Network replay is not a deliberate new submission. A fresh user submission starts a new form-line identity; rejected/cancelled numbers are not recycled.
- Metadata and immutable numbers survive edits and deletes. The bounded operational feed returns metadata for actual rows and pending creates. Numbered acknowledgements are checked against the original identity, base and metadata before local handoff/cleanup.

## End-to-end scrutiny

The smaller design is to keep the existing issuer registration, Income/Expense outbox, sync dispatcher, business core and approval rules. Separate I/E allocator state and durable acceptance/create receipts are necessary to preserve identity through partial form failures, app restarts and rejected approval/history cleanup; a generic numbering framework or a move to Rubber's central queue adds no required behavior.

- Create: `IncomeExpenseModal` row identity → `persistIncomeExpenseSubmissions` local restrictions → `useIncomeExpense` → atomic `enqueueNumberedIncomeCreate` → payload builder → numbered route/RPC → existing dispatcher/core → allocation at actual INSERT. Approval uses the same core; pending never receives a final.
- Retry/handoff: main sender and per-record retry → numbered result validator → `confirmIncomeNumberedEvent` persists outcome before deleting only the exact current command. Terminal receipts reject changed intent and survive disposable approval-history cleanup; a missing capability or wrong identity leaves the original local command intact.
- Edit/delete/read: builder retains metadata, server trigger keeps numbering immutable, existing background sender validates numbered results, bounded feed includes metadata, manager approval/history joins the validated final, and existing report/cash/branch/actor fences still apply.
- Upgrade/recovery: v9 blocked tab closes → v10 adds acceptance store while retaining legacy outbox/Rubber counters; malformed or lost I/E state requires fresh registration. Shared retirement affects new work while old accepted identities and proposals retain their code.

Findings fixed and repro evidence are in the ledger: mutable date comparison, bounded metadata lookup, partial acknowledgement blocking later rows, missing approval display, lost maps, malformed base type, unhandled quota callback and clipped mobile numbers. No unresolved finding is known. Verdict: Local implementation is ready; publishing remains outside this task.
