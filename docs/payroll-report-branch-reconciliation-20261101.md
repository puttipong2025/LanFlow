# ตรวจรายงานรับ–จ่ายสาขากับเงินเดือนส่วนโอน

สถานะล่าสุด: นำขึ้นระบบจริงเฉพาะงานนี้แล้ว เมื่อ 1 พฤศจิกายน 2026 เวลา 22:44 น. ผลตรวจหลังนำขึ้นผ่าน

## ผลตรวจ
ยืนยันปัญหาซ้ำได้ในฐาน Local `supabase_db_webapp` ด้วยข้อมูลจำลองที่ rollback ทุกครั้ง รวมถึงการเรียกขั้นตอนสร้างรายงานจริง ระบบนำส่วนโอนเงินเดือนเข้าเป็นรายจ่ายในรายงานรับ–จ่าย ขณะที่ยอดสะสมหักเฉพาะส่วนสาขาจ่ายแล้ว

เงินเดือนสุทธิ 15,000 บาท ส่วนโอน 10,000 บาท ส่วนสาขาจ่าย 5,000 บาท:
- รายงานปัจจุบันแสดงรายจ่าย 15,000 บาท และบันทึกยอดปิด −15,000 บาท เมื่อยอดเปิดเป็นศูนย์
- ยอดรับ–จ่ายสะสมสาขาลด 5,000 บาท
- ส่วนต่าง 10,000 บาทตรงกับส่วนโอน

## ข้อสรุปที่ผู้ใช้ยืนยัน
1. รับ–จ่ายสาขานับเฉพาะส่วนที่สาขาจ่าย เงินเดือนส่วนโอนคงแสดงประกอบในหมวดโอนเงินโดยไม่รวมยอดรับ–จ่าย
2. ค่าใช้จ่ายดำเนินงานยังนับเงินเดือนสุทธิเต็มจำนวน
3. แก้รายงานเก่าที่ได้รับผลและยอดยกมาต่อเนื่องด้วย คงเลขรายงาน รายการต้นทาง และหลักฐานเดิม ทำตารางก่อน–หลังให้ตรวจสอบก่อนใช้กับระบบจริง

การทดลองแรกใช้ now() เป็น cutoff ใน transaction เดียวกับแนบสลิป จึงยังไม่รับแถวที่บันทึกด้วยเวลาหลังจากเริ่ม transaction ปรับ cutoff ของข้อมูลจำลองให้หลังแนบสลิป แล้วเกิดซ้ำได้อย่างแน่นอน การทดสอบสร้างรายงานจริงยืนยันผลเดียวกัน

## แผนแก้ที่พร้อมนำไปทำ
1. เพิ่ม migration ใหม่แก้ฟังก์ชันบัญชีรายงาน ให้คงแถวเงินเดือน/เงินเบิกส่วนสาขาจ่าย แต่ไม่นำส่วนโอน `time_payroll` เป็นรายจ่ายสาขา ไม่แก้ migration เก่า
2. คง `bank_transfer_source` ไว้เป็นรายการในรายงาน เพื่อเก็บหมวดโอนเงิน สลิป และ report lock ตามเดิม API มีหมวด bankTransfers แยกอยู่แล้ว
3. คงค่าใช้จ่ายดำเนินงานเต็มจำนวนและพฤติกรรมข้อมูล legacy/จ่ายนอกระบบตาม helper เดิม
4. เตรียมรายงานผลกระทบก่อน–หลัง: สาขา เลขรายงาน ยอดเปิดเดิม/ใหม่ ยอดปิดเดิม/ใหม่ และส่วนต่าง เริ่มจากสาขาที่มีรายงาน active ผูกโอน time_payroll และรวมรายงานถัดไปที่รับยอดยกมา
5. คำนวณสายยอดรายงาน active ตามลำดับเดิมภายใน transaction และล็อกสาขา ใช้แนวทาง `private.rebuild_active_report_balance_chain` ที่มีอยู่ โดยจำกัดสาขาที่ได้รับผล ตรวจความสอดคล้องก่อนเขียนและทำซ้ำแล้วต้องไม่เปลี่ยนยอดอีก
6. เก็บรายการก่อน–หลังเป็นหลักฐานการแก้ ไม่ลบรายงาน ไม่ย้ายรายการข้ามรอบ ไม่แก้สลิป ไม่ย้อนแก้ผลนับเงินที่ตรึงไว้ และแจ้งว่าพรีวิว/PDF ที่สร้างใหม่จะใช้ยอดแก้ไข ส่วนไฟล์ที่ส่งออกไปแล้วไม่เปลี่ยนเอง
7. ตรวจ migration/นิยามบนระบบจริงก่อนนำไปใช้ เนื่องจากผลตรวจครั้งนี้ยืนยันเฉพาะ Local

ไม่ควรสร้างรายการปรับปรุงรับ–จ่ายทั่วไปเพื่อกลบส่วนต่าง เพราะทำให้รายการเงินจริงเพิ่มและอาจเปลี่ยนยอดสะสมที่ถูกอยู่แล้ว

## เกณฑ์ตรวจรับเมื่อเริ่มแก้
- เงินเดือนสุทธิ 15,000 / โอน 10,000: รายงานจ่าย 5,000; หมวดโอนแสดง 10,000; ต้นทุนดำเนินงาน 15,000
- โอนทั้งหมด: รับ–จ่ายเป็นศูนย์; สาขาจ่ายทั้งหมด: รับ–จ่ายเต็มจำนวน
- เพิ่ม ลบ แก้ และโอนเกินผ่านสลิป ต้องไม่สร้างรายจ่ายสาขาซ้ำ
- เงินเบิกที่ใช้ transfer_type เดียวกันต้องตรวจด้วย รวม legacy, นอกระบบ, รายการยกเลิก และรายการจากโมดูลอื่น
- รายงานเก่าหลายรอบและสาขาเดียวกัน: ยอดเปิดเท่ากับยอดปิดฉบับก่อนทุกจุด; แก้ซ้ำแล้วไม่บวกซ้ำ
- จำนวนรายการ เลขรายงาน รายการต้นทาง report lock และหลักฐานสลิปคงเดิม
- พรีวิวและ PDF ใช้ยอดเดียวกัน; ทดสอบฐานข้อมูลที่เกี่ยวข้องและเส้นทางอ่านรายงาน

## ขอบเขตการตรวจครั้งแรก ก่อนเริ่มดำเนินงาน
รอบนี้ตรวจและจัดทำข้อสรุป/เอกสาร ยังไม่ได้แก้สูตรแอปหรือใช้ migration ไม่ได้เขียน Cloud ไม่ deploy
Local ปัจจุบันพบรายงาน active ที่มีโอน time_payroll 0 ฉบับ / 0 สาขา จึงยังไม่มีตารางยอดจริงก่อน–หลังให้ตรวจ ต้องอ่านระบบที่พบปัญหาจริงเมื่อเข้าสู่ขั้นดำเนินงาน จำนวนนี้ไม่ใช่จำนวนผลกระทบบน Cloud
ข้อมูลทดสอบทั้งหมด rollback แล้ว และรักษางานที่มีอยู่ก่อนใน working tree
## ผลดำเนินงานหลังผู้ใช้ยืนยัน
สถานะ: แก้และใช้ migration ใน Local แล้ว; Cloud ตรวจแบบอ่านอย่างเดียวและเตรียมตารางก่อน–หลังแล้ว ยังไม่ได้ใช้การแก้กับ Cloud

### การแก้
- เพิ่ม `20261101030000_payroll_report_branch_balance.sql` ตัดเฉพาะส่วนโอน time_payroll ออกจากบัญชีรับ–จ่าย คงแถวเงินเดือน/เงินเบิกส่วนสาขาจ่ายและ helper legacy เดิม
- คง bank_transfer_source ใน report_items, หมวดโอนเงิน, หลักฐานและ report lock เดิม ไม่มีการเปลี่ยน API หรือหน้าจอ
- migration แก้ยอดเปิด–ปิดและลิงก์รายงานก่อนหน้าเฉพาะสายรายงาน active ของสาขาที่มีส่วนโอนซึ่งเคยนับเป็นรายจ่าย รายงาน deleted และสาขาที่ไม่เกี่ยวข้องไม่เปลี่ยน
- ใช้สูตรเดียวกับ rebuild เดิม แต่คำนวณใน migration โดยล็อกตารางรายงานช่วงสั้น แทนเรียก helper ที่จับ advisory lock หลัง table lock เพื่อหลีกเลี่ยงการรอกันกับการสร้างรายงานพร้อมกัน บันทึกยอดก่อน–หลังที่เปลี่ยนใน NOTICE ของ migration; ต้องเก็บผลรันไว้เป็นหลักฐาน
- เพิ่ม `scripts/preview-payroll-report-balances.sql` สำหรับแสดงผลกระทบแบบ read-only ก่อนใช้กับระบบจริง
- อัปเดตเฉพาะนิยามฟังก์ชันบัญชีรายงานใน supabase-schema.sql จาก Local dump; การเปลี่ยนสูตรมีเพียงการเอา UNION ส่วนโอนออก

### หลักฐานตรวจรับ
1. ก่อนแก้: regression 65 ข้อล้มเหลว 17 ข้อ ครอบคลุมเงินเดือนและเงินเบิกที่โอนครบ/เกิน รวมยอดปิดและยอดยกมา
