# แผนลดภาระคิวและการโหลดตารางบิลยาง

สถานะ: ดำเนินการและปล่อย Cloud แยกส่วนคิวแล้วตามด้วย feed — 2026-10-30 ผลและข้อจำกัดอยู่ในเอกสาร verification ของแต่ละส่วน Daily checklist เป็นแหล่งความคืบหน้าที่ผู้ใช้ระบุ

## ขอบเขตที่ผู้ใช้ยืนยัน

ปรับทั้งเวลายืนยันบิลและภาระรวมของระบบ เริ่มจากการลดงานตรวจผู้ส่งซ้ำที่มีผลทดลองแล้ว จากนั้นปรับการโหลดตารางบิล เก็บคิวกลางเป็นโครงสร้างตั้งต้น ประเด็นโครงสร้างที่ยังไม่ได้ตกลงให้ถือเป็นข้อเสนอ

## หลักฐานตั้งต้น

- การตรวจ Cloud ช่วงสั้น 36.243 วินาที: feed 12 ครั้ง ใช้เวลารวม SQL 5,690.61 ms; worker 360 ครั้ง รวม 295.56 ms ตัวเลขนี้ไม่ใช่ CPU และไม่ใช่หลักฐาน peak load
- การทดลองบนสำเนาฐานข้อมูล Local แบบ rollback: คำนวณผู้ส่งงานครั้งเดียวต่อคำสั่งอ่านใน helper ตรวจสิทธิ์สามตัว ลดเวลาประมวลผล SQL รวม 18.11% และ 12.98% ในการทดสอบสองลำดับ
- การลด SQL ดังกล่าวไม่เท่ากับลดเวลาตั้งแต่กดบันทึกจนหน้าจอยืนยันในสัดส่วนเดียวกัน และยังไม่ได้ผ่าน gate สำหรับปล่อย optimization นี้บน Cloud
- รายละเอียดการทดลอง: `output/rubber-queue-load-review-20261030.md` และ `output/rubber-queue-optimization-repeated.json` เป็นหลักฐานเฉพาะเครื่อง ยังไม่ใช่ผลตรวจ production หลังปรับ

## ลำดับงานที่เสนอ

1. กำหนดตัวชี้วัด เกณฑ์ผ่าน และภาระทดสอบที่ผู้ใช้ยอมรับ
2. ปรับ helper ตรวจผู้ส่งด้วย forward migration; ตรวจการแยกผู้ส่ง/สาขา สิทธิ์ปัจจุบัน replay ล็อก และงานพร้อมกัน พร้อมวัดก่อน–หลัง
3. ตรวจ execution plan ของ feed และเหตุที่ทำให้โหลดซ้ำ ก่อนเลือกว่าจะลดงาน SQL ลดการร้องขอ หรือทำทั้งสองส่วน
4. ทดสอบผลลัพธ์ การเรียงหน้า การค้นหา การอนุมัติ และความสดของข้อมูลหลายเครื่อง ก่อนเปรียบเทียบภาระและความเร็ว
5. วาง rollout การสังเกตผลและ rollback หลังได้ข้อสรุปการออกแบบร่วมกัน

## เกณฑ์ความเร็วที่ผู้ใช้ยืนยัน

ผู้ใช้ระบุว่าความเร็วปัจจุบันอยู่ในระดับพอใช้ได้ และหน้างานขึ้นกับความเร็วอินเทอร์เน็ต เป้าหมายหลักจึงเป็นการลดภาระและงานซ้ำ โดยรักษาความเร็วและความถูกต้องปัจจุบัน ไม่กำหนดเกณฑ์ตายตัวว่า 95% ของบิลต้องเสร็จภายใน 3 วินาที

เทียบก่อน–หลังด้วยข้อมูล ภาระงาน และเงื่อนไขเครือข่ายเดียวกัน แยกเวลาประมวลผล SQL ออกจากเวลาตั้งแต่กดบันทึกจนหน้าจอยืนยัน เก็บงานล้มเหลวและการลองใหม่ไว้ในผลวัด ไม่เริ่มจับเวลาใหม่เมื่อส่วนกลางรับงาน ไม่รวมช่วงกรอกข้อมูล การอ่านรูป OCR และการพิมพ์เอกสาร ตัวเลขเป้าหมายที่ยังไม่ผ่านการทดสอบไม่ใช่ SLA บน Cloud

## ความสดของข้อมูลที่ผู้ใช้ยืนยัน

คงพฤติกรรมการเห็นข้อมูลเดิมของเครื่องต้นทางและเครื่องอื่น ไม่เพิ่มช่วงรอหรือขยายระยะ cache เพียงเพื่อให้ตัวเลขภาระลดลง เริ่มจากลดงาน SQL และการร้องขอซ้ำที่ไม่จำเป็น โดยต้องตรวจว่าการยืนยันบิลและการเห็นการเปลี่ยนแปลงยังทำงานเทียบเท่าเดิม ข้อนี้ไม่ได้กำหนดคำรับประกัน realtime ใหม่

## วิธีส่งมอบที่ผู้ใช้ยืนยัน

ปล่อยส่วนคิวก่อน ตรวจผลใช้งานจริง แล้วจึงปล่อยส่วนตารางบิล แยกชุดแก้ การทดสอบ หลักฐานก่อน–หลัง และ rollback ของแต่ละส่วน การยืนยันวิธีปล่อยนี้เป็นข้อสรุปการออกแบบในช่วงวางแผน ไม่ใช่หลักฐานว่าได้ติดตั้งแล้ว

ยังไม่มีการตัดสินใจเชิงสถาปัตยกรรมใหม่ที่ต้องสร้าง ADR และยังไม่มีคำศัพท์ใหม่ที่ตกลงจนต้องเพิ่มใน CONTEXT.md

## ขนาดการใช้งาน

ผู้ใช้ประเมินช่วงพีค 30–40 เครื่องเปิดใช้งานบิลยางพร้อมกัน รวมทุกสาขา ยืนยันว่าสาขาละ 1 เครื่อง และแต่ละสาขาออกบิล 1 บิลทุก 30 วินาที เท่ากับ 60–80 บิลต่อนาทีรวมทุกสาขา

ฐานทดสอบที่เสนอคือ 40 เครื่องกระจาย 40 สาขา สาขาละ 2 บิลต่อนาที รวม 80 บิลต่อนาที ทดสอบขีดจำกัดเพิ่มถึง 80 เครื่องกระจาย 80 สาขา รวม 160 บิลต่อนาที ยังไม่ใช่ความสามารถที่พิสูจน์แล้ว ทดสอบทั้งจังหวะกระจายตามธรรมชาติและการกดพร้อมกัน พร้อมรวมการโหลดหน้าบิล/จำนวนงานตามพฤติกรรมเดิม ไม่วัดเฉพาะคำสั่งบันทึกโดด ๆ

การส่งซ้ำ การเชื่อมต่อกลับหลังออฟไลน์ และงานชนกันในสาขาเดียวคงเป็นกรณีทดสอบความถูกต้อง แม้ไม่ใช่ภาระใช้งานปกติที่ผู้ใช้ระบุ ทดสอบภาระบนสภาพแวดล้อมแยกที่เทียบเคียงได้ ไม่ยิง load test ใส่ Cloud production ที่กำลังใช้งานจริง

## แนวทางโครงสร้างที่ผู้ใช้ยืนยัน

ปรับระบบฐานข้อมูลและคิวเดิมก่อน โดยเก็บสิทธิ์ การตรวจรุ่นข้อมูล การกันคำสั่งซ้ำ ล็อก และขอบเขตธุรกรรมเดิม เริ่มจาก helper ตรวจผู้ส่งสามตัว แล้วตรวจแผนอ่านข้อมูลของ feed เพื่อลดงาน SQL และการโหลดซ้ำโดยไม่เปลี่ยนผลลัพธ์หรือความสดของข้อมูล

ผู้ใช้ยืนยันให้ยังไม่เพิ่มระบบคิว บริการ worker หรือ cache กลางใหม่ เพียงเพื่อเผื่ออนาคต พิจารณาโครงสร้างเพิ่มเติมเมื่อผลทดสอบชี้ข้อจำกัดของระบบเดิมที่แก้เฉพาะจุดไม่ได้ และเสนอ trade-off ให้ผู้ใช้ตัดสินใจอีกครั้ง คงหลักของ ADR-0086 และ ADR-0089 ไม่สร้าง ADR ใหม่ซ้ำเพียงเพื่อบันทึกการปรับประสิทธิภาพที่ย้อนกลับได้

## รายละเอียดการออกแบบและ gate ที่เสนอ

### ระยะ A: สร้าง baseline ที่ทำซ้ำได้

- ใช้ข้อมูลชุดเดียวกัน รุ่นฐานข้อมูลเดียวกัน และ payload/ลำดับงานที่ทำซ้ำได้ บันทึกรุ่นซอร์สและการตั้งค่าของแต่ละรอบ
- วัดภาระปกติ 40 สาขา/80 บิลต่อนาที และสำรวจขีดจำกัด 80 สาขา/160 บิลต่อนาที รวมการเปิดหน้า อ่านข้อมูล และบันทึก ไม่เพิ่มโหลดทดสอบใส่ production
- มีช่วงอุ่นระบบและช่วงวัดคงที่ที่เหมือนกันทุกเวอร์ชัน สลับลำดับก่อน–หลังเพื่อลดอคติจาก cache และแยกรายงาน cold start
- เก็บจำนวนคำสั่งรับ/เสร็จ/ค้าง/ล้มเหลว/ลองใหม่ อายุงานค้าง median/p95 เวลายืนยันบนหน้าจอ จำนวน request เวลารวม SQL และ buffer accesses; CPU/IO รายงานเฉพาะเมื่อวัดแยกได้จริง

### ระยะ B: ลดการตรวจผู้ส่งซ้ำภายในคิว

- เปลี่ยนเฉพาะการประเมินรหัสผู้ส่งใน `rubber_actor_active`, `rubber_actor_manager`, `rubber_actor_location` ให้เป็น scalar subquery โดยใช้ forward migration ใหม่ ไม่แก้ migration เก่า
- รหัสผู้ส่งยังมาจาก protected execution context เดิมหรือ auth fallback ไม่ใช้ cache ข้ามคำสั่งหรือข้ามคำขอ และไม่ยกเลิกการตรวจสิทธิ์ปัจจุบัน
- คง owner/grants, SECURITY DEFINER, search_path, ลำดับล็อก ขอบเขต transaction และการตรวจ revision/generation/ราคาตอนรับงานเดิม
- Gate: ผู้ส่งและสาขาไม่รั่วข้ามกัน การเพิกถอนสิทธิ์/บัญชีไม่ active ถูกปฏิเสธเหมือนเดิม บทบาทผู้จัดการถูกต้อง ไม่มีผลซ้ำเมื่อ retry และผลธุรกิจ/ตัวขวางรายงานตรงเดิม รวมการทดสอบ concurrency และ worker recovery
- เทียบผลและเวลาแบบควบคุม หากความเร็วหรือภาระแย่ลงอย่างทำซ้ำได้ ไม่ปล่อย candidate นั้นแม้ unit tests ผ่าน

### ระยะ C: ลดภาระการโหลดตารางบิล

- ตรวจ execution plan และเหตุที่ทำให้ query ถูกเรียกซ้ำก่อนตัดสินใจแก้ ห้ามถือว่าต้นเหตุจากรูปแบบซอร์สเพียงอย่างเดียว
- ทางเลือกแรกคือคัดและเรียงรายการของหน้าที่ต้องแสดงก่อนสร้าง JSON/items และข้อมูลประกอบ โดยใช้ได้ต่อเมื่อคงเงื่อนไขค้นหา ตัวกรอง รายการอนุมัติ และการเรียงข้ามประเภทเอกสารได้ครบ เงื่อนไขที่มีผลต่อสมาชิกในหน้าต้องถูกประเมินก่อนแบ่งหน้า
- ลด request ที่ซ้ำเฉพาะเมื่อพิสูจน์ว่ารวมได้โดยไม่กลืนการเปลี่ยนแปลงที่มาถึงระหว่างโหลด ไม่แก้ปัญหาด้วยการขยาย polling/cache time
- Gate: response contract เดิม การค้นหา cursor/hasMore ไม่มีแถวซ้ำหรือหาย สิทธิ์ ผู้ขออนุมัติ รายการโอน/รายงาน และค่าที่แสดงตรงเดิม ตรวจการเห็นผลของเครื่องต้นทางและการเปลี่ยนจากเครื่องอื่นด้วย
- เลือกการปรับ SQL และ/หรือการรวม request ตามผลวัด ไม่ผูกแผนไว้กับ rewrite ทั้งฟังก์ชันล่วงหน้า

### ระยะ D: ปล่อยและกู้กลับ

- ผู้ใช้ยืนยันให้ปล่อย B ก่อน สังเกตผล แล้วจึงปล่อย C เพื่อแยกสาเหตุและย้อนได้เป็นส่วน ไม่ปิดคิวสำรองเพื่อทำให้ตัวเลขดีขึ้น
- ก่อนแต่ละส่วน ตรวจ migration ที่จะใช้ สำรองนิยาม/สิทธิ์ฟังก์ชันเดิม และเตรียม forward rollback ที่คืนเฉพาะนิยามที่แก้ ห้ามล้าง jobs/receipts/outbox หรือย้อน migration history
- หยุด rollout เมื่อมีผลธุรกิจผิด แถวหาย/ซ้ำ สิทธิ์ผิด ผลซ้ำจากคำสั่งเดิม งานค้างสะสมโดยไม่มีช่วงระบาย หรือข้อผิดพลาดใหม่ที่สัมพันธ์กับรุ่นที่ปล่อย เปรียบเทียบกับ baseline และโหลดจริง ไม่อ้างว่า load test Local ยืนยัน Cloud แล้ว
- การกู้กลับ B คืน helper เดิมด้วย forward migration; C คืน query/consumer รุ่นที่เข้ากันได้ตามขอบเขตที่แก้ โดยเก็บข้อมูลและผลคำสั่งเดิม ใช้คู่มือคิวเดิมประกอบเมื่อเป็น incident

## ลำดับเริ่มต้นที่ใช้ดำเนินงาน

เริ่มเฉพาะ A และ B: ย้ายการทดลองที่จำเป็นจาก output/ เป็นเครื่องมือทดสอบที่ดูแลต่อได้ สร้าง baseline ตามภาระที่ตกลง ทำ forward migration และ regression tests ของ helper สามตัว เตรียม rollback และสรุปชุดปล่อยส่วนคิวแยกจากงาน feed ระยะ C จะยังไม่รวมในชุดปล่อยแรก และต้องใช้ค่าหลัง B เป็น baseline ใหม่เพื่อแยกผลการปรับแต่ละส่วน
